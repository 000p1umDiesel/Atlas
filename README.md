# mnogobase

**Документы → гибридный поиск, граф знаний и постоянная wiki → ответы с источниками.**

`mnogobase` — Python-пакет и CLI для работы с собственным корпусом документов на русском и английском. Он разбирает файлы, связывает сущности из разных источников, обновляет Markdown-wiki и позволяет сравнивать четыре способа поиска на одних данных. Текущая версия — `0.1.0`. Интерфейсы — CLI в терминале и HTTP API личной базы знаний одного владельца (с CLI-клиентом и чатами).

## 1. Что это такое

`mnogobase` берёт документы (PDF, DOCX, PPTX, XLSX, HTML, Markdown, AsciiDoc, CSV, TXT) и строит из них:

- **векторный индекс** в Qdrant: плотные векторы Qwen3-Embedding (llama.cpp server или другой OpenAI-совместимый сервер) и разреженные BM25 для гибридного поиска;
- **граф знаний** в Neo4j: документы, чанки, сущности, связи между сущностями и чанки-доказательства для каждой связи;
- **wiki** из Markdown-страниц в духе LLM Wiki Карпаты: по странице на важную сущность, со сносками на источники. Wiki открывается в Obsidian и дописывается при каждом новом документе, а не переписывается с нуля.

По этим слоям можно задавать вопросы в четырёх режимах (`rag`, `wiki`, `graph`, `all`) и получать ответ с нумерованными цитатами: файл, страница, id чанка или раздела wiki. Команда `compare` отвечает во всех режимах сразу и сохраняет ответы, время и токены. Для оценки качества на датасете есть [`eval run / score / report`](#14-оценка-hybrid-rag-wikillm-и-graphrag) с пятью метриками Ragas.

Обработка документов строит три связанных представления одного корпуса. На схеме показаны основные записи; подробный порядок операций и восстановления — в [разделе 5](#5-как-это-устроено-внутри). Поиск использует подготовленные данные и описан [отдельно](#57-поиск-и-ответ).

Для просмотра схем используйте Markdown-просмотрщик с поддержкой Mermaid.

**Ключевые решения**

| Вопрос | Решение | Почему |
|---|---|---|
| Векторная БД | Qdrant в Docker | именованные dense и sparse векторы в одной коллекции, встроенный hybrid-поиск (RRF), payload-фильтры, есть GPU-образ |
| Ключевые слова | BM25 как sparse-векторы в Qdrant (`fastembed`, `Qdrant/bm25`, IDF считает Qdrant) | не нужен отдельный Elasticsearch, слияние результатов на стороне БД |
| Граф | Neo4j 5 Community с APOC и GDS | APOC — ограниченный обход для graph/all; GDS — отдельный PageRank и Leiden, готовые оценки помогают упорядочивать найденные связи |
| Извлечение графа | свой конвейер, не LightRAG/Graphiti | полный контроль над чанками Docling, wiki и поиском; три подхода сравниваются на одних данных |
| Разбор и чанкинг | Docling `DocumentConverter` и `HybridChunker` | структурный и токен-осознанный чанкинг, много форматов, OCR |
| Эмбеддер и реранкер | в `config.yaml` — Qwen3-Embedding-0.6B и Qwen3-Reranker-0.6B на llama.cpp; размерность эмбеддингов определяется автоматически | модели меняются через настройки; llama.cpp работает нативно на Mac (`models up`) или в CPU-контейнерах полного стека (`compose.yaml`); любой другой OpenAI-совместимый сервер или облачный API подключается как `serve: api` |
| LLM | один клиент для любого OpenAI-совместимого API | llama.cpp, LM Studio, OpenRouter, OpenAI и прокси подключаются правкой конфига. Структурированный вывод через строгую JSON Schema |
| Состояние | PostgreSQL, одна схема на проект | файлы, этапы, ошибки, кэш извлечения, очередь wiki, очередь заданий, пользователи и учёт LLM; на нём держатся возобновление и инкрементальность |
| Интерфейс | пакет, CLI на Typer и HTTP API на FastAPI для одного владельца | API использует тот же пакет; веб-интерфейс и MCP можно навесить поверх |
| Язык wiki | английский по умолчанию | канонические английские имена сущностей склеивают русские и английские упоминания |
| Логи | structlog: консоль и JSONL-файл; в контейнерах — JSON в stdout | формат готов для Loki/Grafana и трейсинга |

> **Куда отправляются документы.** В текущем `config.yaml` LLM — `gpt-6-luna` на `https://codex.sale/v1`: извлечение, объединение сущностей, генерация wiki и ответов передают текст этому сервису. Эмбеддер, реранкер и VLM настроены локально. Все роли можно перенастроить, поэтому фактический маршрут данных определяется вашим конфигом и переменными окружения. Значение LLM по умолчанию в коде — локальный сервер `http://localhost:8000/v1`; внешний API включается только явно в `config.yaml`. Локальная LLM — в [разделе 7.1](#71-локальная-llm).

### 1.1 Какой режим выбрать

| Режим | Из чего собирается контекст | Когда пробовать | Что учитывать |
|---|---|---|---|
| `rag` — Hybrid RAG | исходные чанки: dense + BM25 → RRF → реранкер → соседние чанки | найти формулировку, число или объяснение в документах | реранкер и соседи управляются настройками |
| `wiki` — WikiLLM | разделы сгенерированных wiki-страниц и цитируемые ими исходные чанки | получить обзор сущности по нескольким упоминаниям | нужна собранная wiki; не каждая сущность проходит `min_mentions` |
| `graph` — GraphRAG | стартовые сущности → окрестность связей → чанки-доказательства | исследовать отношения между объектами | зависит от качества извлечения и поиска стартовых сущностей |
| `all` | три вида контекста с долями общего бюджета и удалением повторов | проверить, помогает ли объединение на вашем вопросе | бюджет делится между режимами; результат оценивайте на своих данных |

Здесь GraphRAG — собственная реализация поиска по графу. В ней нет community summaries и конвейера Microsoft GraphRAG. Все режимы используют один генератор ответа; `compare` помогает увидеть различия, а `eval` — измерить их на наборе вопросов.

### 1.2 Термины за минуту

**Ingest** — загрузка документа в базу знаний. **Чанк** — фрагмент документа с заголовками и страницами. **Dense** — поиск по смысловой близости векторов; **BM25** — поиск по словам. **RRF** объединяет позиции результатов этих двух поисков, **реранкер** заново оценивает найденные фрагменты относительно вопроса. **Entity resolution** объединяет упоминания одной сущности. **Evidence** — исходные чанки, подтверждающие связь или wiki-страницу. **Retrieval** — подбор контекста перед генерацией ответа.

## 2. Установка и первый запуск

### 2.1 Что нужно установить

| Что | Зачем | Проверка |
|---|---|---|
| [Docker Desktop](https://www.docker.com/products/docker-desktop/) | PostgreSQL, Qdrant и Neo4j | `docker info` |
| [llama.cpp](https://github.com/ggml-org/llama.cpp) (`llama-server`) | эмбеддер, реранкер, VLM (и, по желанию, локальная LLM). На Mac — `brew install llama.cpp`, на Linux — собранный `llama-server` в `PATH` | `llama-server --version` |
| [uv](https://docs.astral.sh/uv/) | Python 3.12 и зависимости | `uv --version` |
| [Obsidian](https://obsidian.md) (по желанию) | смотреть wiki и её граф | — |

Python нужен версии **3.12** (`>=3.12,<3.13` в `pyproject.toml`); окружением `.venv` управляет `uv`. Поддерживаемые платформы — macOS (разработка) и Linux (сервер, Docker); Windows не поддерживается. Здесь описан режим разработки: базы в Docker, модели и приложение нативно. Весь стек в контейнерах (API, worker, базы и CPU-серверы моделей) — в [разделе 11](#11-развёртывание).

### 2.2 Первый запуск (один раз)

Все команды выполняются **из корня репозитория**: оттуда читаются `config.yaml` и `.env`, и относительно текущей папки считаются пути `.mnogobase/`, `wiki/`, `logs/`, `runs/`.

```bash
# 1. Для новой копии проекта создайте .env; существующий .env сохраните
cp .env.example .env
#    откройте .env и впишите LLM_API_KEY=<ваш ключ>
#    в .env только секреты (пароли баз, ключи), адреса и порты — в config.yaml
#    в config.yaml задано device: cpu; на Mac с Apple Silicon можно MNOGOBASE_DEVICE=mps

# 2. Базы данных на 127.0.0.1: PostgreSQL (:5432), Qdrant (:6333), Neo4j (:7474, :7687)
deploy/prepare-data.sh                         # один раз: каталоги ./data и jar GDS
docker compose up -d postgres qdrant neo4j

# 3. Python-зависимости (пакет ставится в .venv в режиме редактирования)
uv sync

# 4. Эмбеддер (:8001), реранкер (:8002) и VLM для картинок (:8003) по config.yaml:
#    нативные процессы llama-server. Первый старт качает модели
uv run mnogobase models up

# 5. Проверка: всё должно быть зелёным
uv run mnogobase doctor
```

> **Первый запуск дольше обычного.** `mnogobase models up` качает GGUF эмбеддера, реранкера и VLM с Hugging Face, а первый `ingest` — модели разметки и OCR Docling и BM25 `Qdrant/bm25`. Токенайзер чанкера по умолчанию (`chunking.tokenizer: auto`) у llama.cpp берётся из самого GGUF через `/tokenize` сервера эмбеддера, у `serve: api` — HF-токенайзер репозитория, который сервер сообщает в `/v1/models` (несколько МБ), или `/tokenize` сервера. Если Hugging Face откажет в доступе (закрытый репозиторий), примите лицензию на странице модели и выполните `hf auth login` (или задайте `HF_TOKEN`).

### 2.3 Файл .env

`.env` читается из текущей папки при старте любой команды. Переменные, уже заданные в окружении, имеют приоритет над `.env`. **`.env` никогда не коммитится** (он в `.gitignore`).

| Переменная | Нужна | Что это |
|---|---|---|
| `LLM_API_KEY` | для внешнего LLM | ключ OpenAI-совместимого эндпоинта. Имя переменной задаётся в `llm.api_key_env`. Если переменная пуста, клиент отправляет заглушку `local` — локальному llama.cpp без `--api-key` ключ не нужен |
| `NEO4J_PASSWORD` | да | пароль Neo4j. Имя переменной задаётся в `neo4j.password_env`. `compose.yaml` берёт этот же пароль при первом создании базы |
| `POSTGRES_PASSWORD` | да | пароль роли `mnogobase`: им Compose создаёт базу, и с ним Python подключается к адресу из `database.*` (имя переменной — `database.password_env`) |
| `DATABASE_URL` | нет | полный DSN, переопределяет `database.host/port/name/user` и пароль (имя переменной — `database.url_env`); нужен тестам и нестандартным подключениям |
| `QDRANT_API_KEY` | для `compose.yaml` | API-ключ Qdrant в полном стеке (раздел [11](#11-развёртывание)) |
| `HF_TOKEN` | если Hugging Face требует авторизацию | токен для скачивания закрытых моделей (GGUF) и токенайзера, когда он берётся с Hugging Face |
| `MNOGOBASE_API_URL` | по желанию | адрес API для `mnogobase client` (раздел [16](#16-http-api-и-клиент)) |
| `MNOGOBASE_*` | по желанию | переопределение любого ключа `config.yaml` (раздел [6.2](#62-переопределение-через-переменные-окружения)) |

### 2.4 Проверка окружения (doctor)

`uv run mnogobase doctor` печатает таблицу проверок и завершается с кодом 1, если хоть одна проверка не прошла. Предупреждение (`warn`) ошибкой не считается.

| Проверка | Что делает | Типичный провал |
|---|---|---|
| `device` | выбирает устройство для Docling: CUDA → MPS → CPU (или то, что задано в `device`) | — |
| `database` | подключение к PostgreSQL по `database.*` и `POSTGRES_PASSWORD` (или `DATABASE_URL`), печатает схему проекта | не задан `POSTGRES_PASSWORD`, база не запущена, неверный пароль |
| `models` | `GET <url>/models` у сервера эмбеддера и (при `enabled`) реранкера и VLM: отдаёт ли он `model` из конфига | `... is not reachable: start the local models with mnogobase models up`, `<model> is not served by <url> (it serves ...)` |
| `tokenizer` | загружает токенайзер чанкера: при `auto` — `/tokenize` сервера эмбеддера (`serve: llamacpp`) или, у `api`, репозиторий из `root` в `/v1/models` либо `/tokenize` сервера; иначе HF-репозиторий из `chunking.tokenizer` | `TokenizerError: ...` (см. раздел [9](#9-диагностика-и-частые-проблемы)) |
| `llm` | `GET <llm url>/models` с ключом; 404/405 считаются нормой (`models endpoint not available`) | 401/403 (неверный ключ), `<model> is not served by <url>` |
| `qdrant` | доступность и размерность коллекции `mb_chunks` (при `embedder.dim: auto` — против размерности, которую вернул эмбеддер; если он недоступен, размерность не сравнивается) | `mb_chunks has dim 768, config 512: run mnogobase reindex` (после смены `embedder.dim`), `mb_chunks has dim 2560, embedder 1024: ...` (после смены модели при `auto`) |
| `neo4j` | подключение с логином и паролем | `ServiceUnavailable`, `AuthError` |
| `graph_plugins` | версии APOC и GDS и наличие нужных процедур (раздел [5.8](#58-apoc-и-gds)) | только `warn`: без плагинов обычные режимы работают, `graph analyze` — нет |
| `index` | совпадает ли эмбеддер, которым построен индекс (модель, размерность, шаблоны), с текущим конфигом | `index was built with ..., config now uses ...: run mnogobase reindex` |
| `types` | менялись ли типы сущностей после загрузки документов | только `warn`, см. раздел [6.3](#63-типы-сущностей) |

Команды `ingest`, `remove`, `wiki build`, `ask` и `compare` перед стартом сами выполняют облегчённую проверку (`models`, `llm`, `qdrant`, `neo4j`; `ingest` — ещё и `tokenizer`), `reindex` — без `llm` и без сверки размерности коллекций (он их пересоздаёт), `reset` — только `qdrant` и `neo4j`. Если сервис недоступен, команда печатает причину, советует `mnogobase doctor` и завершается с кодом 2.

### 3.1 Куда класть документы

Кладите файлы в папку **`documents/`** в корне репозитория (она в `.gitignore`, в git ничего не попадёт):

```bash
mkdir -p documents
cp ~/Downloads/*.pdf documents/
```

- Подпапки можно любые: `ingest` обходит папку рекурсивно.
- Скрытые файлы и папки (имя начинается с `.`) пропускаются.
- Берутся только расширения из `parsing.extensions`: `pdf, docx, pptx, xlsx, html, htm, md, adoc, csv, txt` и картинки `png, jpg, jpeg, tif, tiff, bmp, webp` (скриншоты). Остальные файлы молча игнорируются.
- Документы могут быть на русском и на английском вперемешку. Страницы wiki пишутся на языке из `wiki.language` (по умолчанию `en`).

Папка может быть любой: `documents/` — просто соглашение. `ingest` принимает и отдельные файлы, и несколько путей сразу.

### 3.2 Загрузка документов (ingest)

```bash
uv run mnogobase ingest documents/
```

Для каждого файла по очереди выполняются этапы:

| Этап | Что происходит | Где результат |
|---|---|---|
| `parse` | Docling разбирает файл: текст, заголовки, таблицы, OCR для сканов и скриншотов; при `vision.enabled` графики, схемы и скриншоты описывает VLM, описание становится текстом документа | `.mnogobase/cache/<doc_id>.json`, картинки и `images.json` в `.mnogobase/cache/<doc_id>/images/` |
| `chunk` | HybridChunker режет документ по структуре на чанки до `chunking.max_tokens` (512) токенов | `.mnogobase/cache/<doc_id>.chunks.json` |
| `embed` | каждый чанк (с заголовками раздела) → плотный вектор Qwen3-Embedding и BM25 | Qdrant `mb_chunks`; узлы `Document`, `Chunk`, связи `HAS_CHUNK`, `NEXT` в Neo4j |
| `extract` | LLM достаёт из каждого чанка сущности и связи (параллельно, до `llm.concurrency` запросов) | кэш `extraction_cache` в PostgreSQL |
| `graph` | сущности сливаются с уже известными (в том числе RU и EN), связи пишутся в граф | Neo4j `Entity`, `MENTIONS`, `RELATED`; Qdrant `mb_entities`; `entity_ids` в payload чанков |
| wiki | после всех файлов: страницы сущностей с новыми упоминаниями создаются или дописываются | `wiki/entities/*.md`, `wiki/index.md`, `wiki/log.md`; Qdrant `mb_wiki_pages` |

Как это работает:

- **Инкрементально.** Документ опознаётся по хешу содержимого (`doc_id`). Повторный `ingest` той же папки пропускает неизменённые файлы. Изменённый файл сначала удаляет свою старую версию из Qdrant, Neo4j и wiki, затем загружается как новый — без дублей. Переименованный или перемещённый файл без изменений не загружается заново: ссылки в источниках переводятся на новый путь, а wiki-страницы, которые цитируют документ, показывают новое имя файла после ближайшей сборки wiki (`ingest` без `--no-wiki` или `wiki build`).
- **Возобновляемо.** Если процесс прервался (Ctrl+C, упал сервис), следующий `ingest` продолжит каждый файл с первого незавершённого этапа. Результаты LLM кэшируются, поэтому повторно оплачивать извлечение не нужно.
- **Ошибки изолированы.** Один сломанный файл не останавливает остальные. Внутри `extract` неудачные чанки допускаются, пока их доля не больше `extract.max_failed_ratio` (0.2). Упавший файл при следующих запусках пропускается с сообщением `stage <этап> failed earlier; rerun with --retry-failed`.

Варианты:

```bash
uv run mnogobase ingest documents/statya.pdf        # один файл
uv run mnogobase ingest documents/ --no-wiki        # без обновления wiki (быстрее; wiki можно собрать потом)
uv run mnogobase ingest --retry-failed              # перезапустить все упавшие файлы (пути берутся из registry)
uv run mnogobase ingest documents/ --retry-failed   # перезапустить упавшие среди этих путей и догрузить новые
```

Пока `ingest` работает, в терминале обновляется прогресс:

```text
⠋ files                                   ━━━━━━━━━━━━━━━              4/12  0:21:40 3 processed · 1 skipped
⠋ Attention Is All You Need.pdf · extract ━━━━━━━━━━━━━━━━━━━━╸        43/96 0:03:12 2 failed
```

- верхняя строка — файлы: сколько готово из найденных (с разбивкой processed / skipped / failed) и сколько времени идёт прогон;
- нижняя — текущий файл и его этап (`parse`, `chunk`, `embed`, `extract`, `graph`). На `extract` видно, сколько чанков из общего числа уже извлечено (попадания в кэш тоже считаются, поэтому возобновлённый прогон проходит быстро) и сколько не удалось; на `graph` — сколько сущностей слито; `parse`, `chunk` и `embed` показывают только время;
- после всех файлов — шаги wiki: `wiki evidence` (поиск доказательств), `wiki draft` (LLM пишет страницы) и `wiki write` (запись страниц), каждый с числом страниц.

`wiki build` и `reindex` показывают такие же полосы для своих шагов. Когда команда заканчивается, полосы исчезают и печатается сводка; вне терминала (пайп, CI) прогресс не рисуется. Подробные времена каждого этапа — в `logs/mnogobase.jsonl` (раздел [4.5](#45-логи-logsmnogobasejsonl)). Служебные сообщения библиотек (INFO от RapidOCR, полосы загрузки моделей Hugging Face) скрыты, предупреждения и ошибки печатаются как раньше.

В конце печатается сводка `run <run_id>: processed N, skipped N, failed N`, отчёт wiki и список упавших файлов с причиной. Код выхода 1, если упал хоть один файл или хоть одна wiki-страница.

> Отдельной команды «только чанкирование» нет: чанки получаются на этапе `chunk` внутри `ingest`. Посмотреть их можно в `.mnogobase/cache/<doc_id>.chunks.json`, в Qdrant (раздел 4.2) или в Neo4j (раздел 4.1).

### 3.3 Сборка wiki (wiki build)

```bash
uv run mnogobase wiki build         # обновить страницы сущностей с новыми упоминаниями
uv run mnogobase wiki build --all   # перегенерировать все страницы (например, после смены языка или промпта)
```

`ingest` без `--no-wiki` сам вызывает сборку wiki в конце. Отдельно `wiki build` нужен после `ingest --no-wiki`, после изменения настроек `wiki.*` или промпта `wiki_page.md`, а также для повтора упавших страниц (они остаются в очереди). Печатается отчёт `wiki: created N, updated N, deleted N, skipped N, failed N`; код выхода 1, если какая-то страница не собралась.

Ошибки при `wiki build --all` также оставляют страницы в очереди: для повтора достаточно обычного `wiki build`. Если новая страница не записалась, ссылки на неё исключаются из остальных страниц без повторных запросов к LLM.

### 3.4 Вопросы (ask и compare)

```bash
uv run mnogobase ask "Что такое механизм внимания?"               # режим all (по умолчанию)
uv run mnogobase ask "Что такое механизм внимания?" --mode graph  # или -m rag | wiki | graph | all
uv run mnogobase ask "Что такое механизм внимания?" --k 12        # больше результатов на каждый поиск
uv run mnogobase compare "Что такое механизм внимания?"           # все 4 режима рядом
```

`--k` должен быть положительным целым числом; значения 0 и меньше отклоняются до подключения к сервисам.

| Режим | Откуда берётся контекст |
|---|---|
| `rag` | ближайшие чанки из Qdrant `mb_chunks` (гибридный поиск dense + BM25, слияние RRF) |
| `wiki` | разделы wiki-страниц из `mb_wiki_pages` (тот же гибридный поиск) и чанки, на которые эти разделы ссылаются |
| `graph` | сущности, найденные по вопросу, их окрестность в графе на `graph.hops` шага и чанки-доказательства сильнейших связей |
| `all` | всё вместе: каждый режим получает долю общего бюджета токенов (`retrieval.budget`), повторы убираются |

Ответ печатается в рамке с режимом и временем, под ним — таблица источников: номер `[n]`, отметка `cited` (LLM сослалась на этот номер в тексте), вид (`chunk`, `wiki`, `entity`, `relation`), файл и страница, `ref` (id чанка, раздела wiki или связи) и начало текста. Язык ответа задаёт `retrieval.answer_language` (в `config.yaml` — `ru`; `auto` — язык вопроса). Вопрос не на английском (больше 30% букв не латиница) перед поиском переводится на английский (задача LLM `query`), и поиск идёт по обеим формулировкам; отключается `retrieval.translate: false`. Если источников нет, печатается `The knowledge base has no relevant sources for this question.`

`compare` печатает таблицу: режим, ответ, процитированные источники, задержка, токены LLM, размер контекста, и дописывает по строке на режим в `runs/compare.jsonl` (раздел 4.4; больше 20 МБ — файл переименовывается в `compare.1.jsonl`).

`ask` и `compare` работают только внутри проекта (нужны схема registry PostgreSQL и локальный `.mnogobase/postgresql-project.json`), иначе завершаются с кодом 2 и ничего не создают. Блокировку `ingest` они не берут: спрашивать можно и во время загрузки.

### 3.5 Состояние (status)

```bash
uv run mnogobase status
```

Показывает: файлы по статусам (`done`, `failed`, `processing`, `pending`), таблицу этапов (`done / failed / pending / running`), число сущностей в очереди на обновление wiki, незавершённые удаления старых версий документов, предупреждение о смене типов сущностей и таблицу ошибок (`doc_id`, этап, текст ошибки). Вне проекта сообщает, что проекта нет, и завершается с кодом 0, ничего не создавая.

### 3.6 Пересчёт векторов (reindex)

```bash
uv run mnogobase reindex
```

Нужен после смены эмбеддера (модель, размерность, шаблоны): `ingest`, `wiki build`, `ask` и `compare` сами замечают такую смену и останавливаются с просьбой запустить `reindex`. Сначала проверяет, что эмбеддер выдаёт вектор размерности `embedder.dim` (при `auto` — просто что он отвечает; иначе останавливается, ничего не тронув), затем удаляет и заново создаёт три коллекции Qdrant с новой размерностью и пересчитывает векторы: чанки — из кэша `.mnogobase/cache/<doc_id>.chunks.json` (если кэша нет, текст берётся из Neo4j), сущности — из Neo4j, разделы wiki — из файлов `wiki/entities/*.md`. Граф, wiki-файлы и кэш извлечения не меняются, LLM не вызывается. Печатает `reindexed: N chunks, N entities, N wiki sections`.

Пока `reindex` идёт, индекс помечен как незавершённый: если его прервать, `ingest` и `ask` откажутся работать, пока `reindex` не будет запущен снова и не дойдёт до конца. Пример смены модели и размерности — рецепт [7.4](#74-сменить-эмбеддер-или-размерность).

До удаления коллекций проверяется чтение документов из кэша или Neo4j и всех зарегистрированных wiki-файлов. Повреждённый кеш чанков восстанавливается для пересчёта из Neo4j. Если данных не хватает или их нельзя прочитать, команда сообщает `missing or unreadable ...; nothing was changed` и сохраняет индекс. Восстановите недостающий файл из резервной копии; wiki можно пересобрать через `wiki build --all` с прежним эмбеддером. Исчезновение данных уже во время пересчёта оставляет индекс незавершённым и требует повторного `reindex` после восстановления.

### 3.7 Полный сброс (reset)

```bash
uv run mnogobase reset            # покажет, что удалит, и спросит подтверждение
uv run mnogobase reset --yes      # без вопроса
```

Область действия `reset`:

- вне проекта (нет маркера PostgreSQL) он отказывается работать даже с `--yes` (код 2): неверная папка или `--config` не должны стереть чужие данные;
- сначала ставит в registry флаг `reset-in-progress`, затем удаляет Qdrant, граф (пачками по 1000 узлов, чтобы большой граф не упёрся в heap Neo4j), кэши и wiki, а registry очищает последней. Прерванный `reset` не оставит registry, которая считает удалённые документы загруженными: пока флаг стоит, остальные команды отказываются работать и просят запустить `reset` ещё раз;
- перед подтверждением показывает, что именно удалит: **все узлы в базе Neo4j по умолчанию** (держите отдельный Neo4j на проект), коллекции Qdrant с префиксом `mb_`, таблицы registry выбранного проекта и файловые кэши в `.mnogobase/` (схема БД сохраняется, папка `cache/` удаляется), а из wiki — только то, что создал сам: `entities/`, `index.md`, `log.md`, `log.1.md`. Другие файлы в `wiki/` (например, ваши заметки и настройки Obsidian в `.obsidian/`) не трогаются, папка удаляется, только если опустела.

Очередь заданий (таблица PostgreSQL `jobs`), загруженные через API файлы и их записи, пользователи, сессии, диалоги, учёт LLM, измерения `processing.jsonl`, логи и сохранённые отчёты остаются. Перед сбросом остановите worker; повторная постановка неизменённых файлов описана в [разделе 15.1](#151-очередь-и-наблюдение).

Отказ на вопросе подтверждения завершает команду с кодом 1.

### 3.8 Все команды

Глобальная опция `--config/-c PATH` ставится **перед** командой: `uv run mnogobase -c other.yaml status`. Без неё используется путь из `$MNOGOBASE_CONFIG` или `./config.yaml`; если файла `./config.yaml` нет, берутся значения по умолчанию из кода.

| Команда | Что делает | Проверка сервисов | Блокировка |
|---|---|---|---|
| `doctor` | все проверки окружения (раздел 2.4) | — | нет |
| `status` | сводка по файлам, этапам, очереди wiki, удалениям и ошибкам | — | нет |
| `ingest PATH... [--no-wiki] [--retry-failed]` | загрузка документов | models, tokenizer, llm, qdrant, neo4j | да |
| `remove [PATH...] [--missing] [--dry-run] [--yes]` | забыть источники и обновить граф, индексы и wiki, сохранив исходные файлы | models, llm, qdrant, neo4j; без сервисов при preview | да |

Команды `ingest`, `remove`, `wiki build`, `reindex`, `reset`, `eval ingest`, `eval run` и обработка задания worker используют общую PostgreSQL advisory lock корпуса. Это не позволяет менять корпус во время экспериментальной генерации ответов. Обычные пишущие команды при занятой блокировке завершаются; worker откладывает обработку, наблюдатель продолжает пополнять очередь. `ask` и `compare` блокировку не берут, поэтому во время записи могут видеть промежуточное состояние.

В каталоге эксперимента `eval` используется отдельная `.eval.lock`. Один worker на проект обеспечивается PostgreSQL advisory lock. Очередь `jobs` и registry используют отдельные таблицы одной схемы PostgreSQL. Для нескольких наблюдаемых папок повторяйте `--watch`, для режимов и метрик — `--mode` и `--metric`. Полные опции доступны через `uv run mnogobase COMMAND --help`.

**Коды выхода:**

| Код | Когда |
|---|---|
| 0 | успех; `status` вне проекта |
| 1 | `doctor` нашёл проблему; в `ingest` / `remove` / `wiki build` есть ошибки; отказ в подтверждении `reset` или `remove`; в `eval run` / `score` / `benchmark` есть неполные/ошибочные результаты; `worker --once` оставил незавершённые задания |
| 2 | ошибка конфига; сервис недоступен на предварительной проверке; блокировка занята; нет проекта (`ask`, `compare`, `remove`, `reset`); индекс построен другим эмбеддером, другой размерности или с другими шаблонами; `reindex`: эмбеддер выдаёт не ту размерность; не удаётся завершить удаление старой версии документа |

### 3.9 Удаление документов (remove)

```bash
uv run mnogobase remove documents/old.pdf --dry-run  # показать выбор без удаления и вызовов моделей
uv run mnogobase remove documents/old.pdf --yes      # удалить знания, сохранить файл на диске
uv run mnogobase remove documents/archive/ --yes     # забыть зарегистрированные файлы каталога
uv run mnogobase remove --missing --dry-run          # посмотреть исчезнувшие источники всей базы
uv run mnogobase remove --missing --yes              # убрать их из базы
uv run mnogobase remove documents/ --missing --yes   # проверить только указанный каталог
```

Без `--yes` команда показывает выбранные пути и запрашивает подтверждение. Пути могут уже отсутствовать на диске: выбор идёт по registry, включая вложенные каталоги. Неизвестный путь ничего не удаляет. При `--missing` ошибка доступа к файлу прерывает выбор, а не считается исчезновением источника.

Если есть другая зарегистрированная копия того же содержимого, документ сохраняется, а пути цитат переводятся на оставшуюся копию. При удалении последней копии убираются исходные чанки из dense/BM25-индекса, их записи и подтверждения связей в графе, сущности без упоминаний, кэши и страницы без источников. Затронутые страницы wiki и ссылки пересобираются; `index.md` обновляется.

Сводные описания затронутых сущностей и связей не имеют привязки отдельных фраз к источникам, поэтому сбрасываются; векторы сохранившихся сущностей пересчитываются по имени. Их исходные подтверждения остаются в графе. Затронутые сгенерированные страницы и их поисковый индекс очищаются до генерации, чтобы старые утверждения не попали в новый текст. Если LLM недоступна, страницы остаются в очереди на пересборку: повторите `uv run mnogobase wiki build` (ошибка страницы даёт код 1).

Прерванное каскадное удаление записывается в `pending_removals`. Следующие `remove`, `ingest` или `wiki build` доводят его до конца, даже если забываемый исходный файл всё ещё существует. Ошибка каскада даёт код 2 с идентификатором документа. `status` показывает незавершённые удаления.

Команда сохраняет файлы на диске. Повторный `ingest` возвращает их в базу; watcher и задания очереди также могут импортировать существующий источник. Если документ не должен возвращаться, уберите его из наблюдаемого каталога. Сам watcher удаление знаний не запускает: после удаления файлов используйте `remove --missing`. Исторические логи и результаты экспериментов сохраняются.

## 4. Как смотреть результаты

### 4.1 Граф в Neo4j

1. Откройте **http://localhost:7474**.
2. Подключение: `neo4j://localhost:7687`, пользователь `neo4j`, пароль из `.env` (по умолчанию `mnogobase-dev`).
3. **Стиль (один раз).** Выполните в строке запроса `:style`, затем перетащите в открывшуюся панель файл [`docs/neo4j/mnogobase.grass`](docs/neo4j/mnogobase.grass). У сущностей появятся имена, у связей — предикаты, у документов и чанков — свои цвета и подписи (заголовок документа, номер чанка).
4. **Цвет по типу сущности (по желанию).** Тип хранится в свойстве `type`; чтобы раскрасить узлы, добавьте его как метку (стиль выше уже содержит цвета для всех 18 типов по умолчанию, см. раздел 6.3):

   ```cypher
   MATCH (e:Entity) CALL apoc.create.addLabels(e, [e.type]) YIELD node RETURN count(node);
   ```

   Повторяйте после новых `ingest`. mnogobase эти метки не использует и не мешает им.

Готовые запросы (вставлять в строку запроса Neo4j Browser):

```cypher
// Весь граф знаний: сущности и связи между ними (самые сильные связи)
MATCH (a:Entity)-[r:RELATED]->(b:Entity)
RETURN a, r, b ORDER BY r.weight DESC LIMIT 300;
```

```cypher
// Окрестность одной сущности на 2 шага (замените имя)
MATCH (e:Entity) WHERE toLower(e.name) CONTAINS 'transformer'
MATCH p = (e)-[:RELATED*1..2]-(:Entity)
RETURN p LIMIT 150;
```

```cypher
// Самые упоминаемые сущности
MATCH (e:Entity)
RETURN e.name AS name, e.type AS type, e.mention_count AS mentions, e.aliases AS aliases
ORDER BY mentions DESC LIMIT 30;
```

```cypher
// Документ → его чанки → сущности, которые в них упоминаются
MATCH (d:Document)-[:HAS_CHUNK]->(c:Chunk)-[:MENTIONS]->(e:Entity)
WHERE d.path CONTAINS 'statya'          // часть имени файла
RETURN d, c, e LIMIT 200;
```

```cypher
// Чанки одного документа по порядку (как его порезал чанкер)
MATCH (d:Document)-[:HAS_CHUNK]->(c:Chunk)
WHERE d.path CONTAINS 'statya'
RETURN c.idx AS idx, c.headings AS headings, c.n_tokens AS tokens, left(c.text, 200) AS text
ORDER BY idx;
```

```cypher
// Откуда взят факт: связь и тексты чанков-доказательств
MATCH (a:Entity)-[r:RELATED]->(b:Entity)
WHERE toLower(a.name) CONTAINS 'transformer'
UNWIND r.evidence AS cid
MATCH (c:Chunk {chunk_id: cid})<-[:HAS_CHUNK]-(d:Document)
RETURN a.name, r.predicate, b.name, d.path, c.page_start, left(c.text, 200) LIMIT 50;
```

```cypher
// Wiki-страницы и ссылки между ними
MATCH (p:WikiPage)-[l:LINKS_TO]->(q:WikiPage) RETURN p, l, q LIMIT 200;
```

```cypher
// Сущности, которые слились из русских и английских упоминаний (есть кириллические алиасы)
MATCH (e:Entity) WHERE any(a IN e.aliases WHERE a =~ '.*[а-яА-ЯёЁ].*')
RETURN e.name, e.type, e.aliases ORDER BY e.mention_count DESC LIMIT 50;
```

Полная схема графа — в разделе [5.4](#54-модель-данных).

|---|---|---|

### 4.3 Wiki в Obsidian

1. В Obsidian: **Open folder as vault** → выберите папку **`wiki/`** в корне репозитория. Она появится после первого `ingest` (или `wiki build`).
2. Начните с **`index.md`**: это оглавление всех страниц, сгруппированное по типам сущностей. В **`log.md`** — журнал прогонов: время, `run_id`, обработанные документы и какие страницы созданы, обновлены или удалены.
3. Страницы сущностей лежат в `entities/<slug>.md`. Каждая страница содержит:
   - свойства (frontmatter): `id` (это `entity_id`), `type`, `aliases`, `sources` (число разных файлов-источников), `updated`, `version`. `aliases` Obsidian использует при поиске и в подсказках ссылок, поэтому русские и английские названия находят одну страницу;
   - текст со сносками `[^chunk_id]`: каждое утверждение ссылается на чанк-источник, а внизу в разделе **Sources** указаны файл и страница;
   - раздел **Related**: связи из графа (`predicate → [[slug|Имя]]` для исходящих, `←` для входящих). Ссылкой связь становится, только если у соседа есть страница.
4. **Граф:** `Cmd/Ctrl+G` открывает общий граф, «Open local graph» в меню страницы — окрестность текущей страницы.
5. **Раскраска по типам и фильтр** настраиваются сами: каждый `wiki build` дописывает в `wiki/.obsidian/graph.json`
   - фильтр `-path:/^(index|log)\.md$/`: `index.md` и `log.md` пропадают из графа, но остаются в списке файлов и в поиске (регулярное выражение нужно, потому что `-file:log` скрыл бы и страницы вроде `logistic-regression`);
   - по цветовой группе на каждый тип из `extract.entity_types` с запросом по свойству (`[type:Person]`, `[type:"Research Area"]` для имён с пробелами). Цвета берутся по порядку из фиксированной палитры, поэтому при тех же типах они совпадают от сборки к сборке; `Other` — серый.

   Добавляется только недостающее: ваш фильтр, ваши группы и перекрашенные вами типы остаются, группы удалённых из конфига типов не удаляются, нечитаемый `graph.json` не трогается. Если хранилище открыто во время сборки, Obsidian может перезаписать файл своей копией настроек: тогда закройте и откройте хранилище и запустите `wiki build` ещё раз. Отключается `wiki.obsidian: false`; `reset` папку `.obsidian/` не трогает.

Что важно знать:

- **Не редактируйте `entities/*.md` вручную:** при следующем обновлении страницы LLM перепишет её на основе прежнего текста и новых фактов, ручные правки могут потеряться. Свои заметки кладите рядом, например в `wiki/notes/`. Их не трогает ни `wiki build`, ни `reset`. В заметках можно ссылаться на страницы сущностей: `[[transformer]]`.
- Страница создаётся для сущностей, которые упомянуты не менее чем в `wiki.min_mentions` чанках (по умолчанию 2) и для которых нашлись чанки-доказательства.
- Папка `wiki/` в `.gitignore` (это производные данные). Если команде нужно хранить wiki в git, уберите её оттуда.

### 4.4 Сравнение режимов (runs/compare.jsonl)

Каждый `compare` дописывает 4 строки JSON (по одной на режим) с полями:

| Поле | Что это |
|---|---|
| `ts` | время прогона (UTC, одинаковое для 4 строк) |
| `question`, `mode`, `answer` | вопрос, режим, текст ответа |
| `alt_queries` | дополнительные формулировки для поиска (английский перевод вопроса; пусто, если перевод не нужен или не удался) |
| `sources` | список источников: `n`, `kind`, `ref`, `path`, `page`, `snippet`, `cited` |
| `latency_ms` | перевод запроса, поиск и генерация вместе |
| `tokens_in`, `tokens_out` | токены LLM на ответ (по данным `usage` эндпоинта) |
| `context_tokens` | оценка размера контекста (символы / 4) |
| `config_hash` | хеш настроек `llm`, `embedder`, `chunking`, `retrieval`, `graph`: сравнивайте прогоны только с одинаковым хешем |

Примеры с `jq`:

```bash
# режим, задержка, токены и число процитированных источников
jq -r '[.mode, .latency_ms, .tokens_in, .tokens_out, ([.sources[] | select(.cited)] | length)] | @tsv' runs/compare.jsonl

# все ответы на конкретный вопрос
jq 'select(.question | test("внимани")) | {mode, answer}' runs/compare.jsonl
```

### 4.5 Логи (logs/mnogobase.jsonl)

Команды пишут структурированный лог в `logs/mnogobase.jsonl` (JSON по строкам, ротация по 10 МБ, хранится 5 старых файлов). В консоль выводятся только предупреждения и ошибки. В контейнерах (`MNOGOBASE_LOG_FORMAT=json`, задано в `Dockerfile`) те же JSON-строки идут в stdout, файл не пишется: смотрите `docker compose logs`. Трейсбеки пишутся без локальных переменных, чтобы в лог не попадали ключи и тексты документов.

Общие поля: `ts`, `level`, `event`, `run_id` (у `ingest` и `wiki build`), `doc_id` (внутри обработки файла). Основные события:

| `event` | Поля | Когда |
|---|---|---|
| `stage_done` / `stage_failed` | `stage`, `duration_ms`, `path`; при ошибке `error_type`, `error`, `exception` | каждый этап каждого файла |
| `parsed` | `title`, `n_pages`, `n_images` | после Docling |
| `llm_call` | `task` (`extract`, `resolve`, `wiki`, `answer`, `query`), `model`, `tokens_in`, `tokens_out`, `retries`, `duration_ms` | каждый вызов LLM |
| `llm_invalid_json` | `task`, `error` | ответ LLM не прошёл схему, идёт повтор с текстом ошибки |
| `extract_failed` / `extract_partial` | `chunk_id`, `error` / `failed`, `total` | неудачные чанки на этапе `extract` |
| `entity_merged` | `name`, `into`, `score`, `method` (`vector`, `llm` или `llm_name` — кандидат по ключу имени, `score` пустой) | слияние сущностей |
| `wiki_built` / `wiki_page_failed` | счётчики / `entity_id`, `error` | сборка wiki |
| `ingest_done`, `ingest_file_failed` | счётчики / `path`, `error` | итог `ingest` |
| `resuming_interrupted_stages`, `resuming_document_removal`, `document_removed`, `document_repointed`, `document_needs_reingest` | | восстановление, удаление старых версий, переименование |
| `entity_types_changed` | `detail` | типы сущностей поменялись |
| `reindex_done`, `reset_done` | счётчики | обслуживание |
| `embedder_signature_upgraded` | `old`, `new` | старая подпись индекса `model_id:dim` переписана в формате с хешем шаблонов |
| `job_failed`, `job_deferred`, `job_timeout` | `job_id`, `error_type` / `timeout_s` | задание worker упало, отложено из-за недоступного сервиса или превысило `jobs.timeout_s` |
| `login_failed` | `user` (хеш имени) | неудачный вход в API (банит fail2ban по журналу nginx, см. `deploy/fail2ban/`) |

Примеры с `jq`:

```bash
# сколько секунд занял каждый этап в сумме
jq -s 'map(select(.event=="stage_done")) | group_by(.stage)
       | map({stage: .[0].stage, seconds: ((map(.duration_ms) | add) / 1000)})' logs/mnogobase.jsonl

# все ошибки
jq 'select(.level=="error") | {ts, event, doc_id, stage, error_type, error}' logs/mnogobase.jsonl

# вызовы и токены LLM по задачам
jq -s 'map(select(.event=="llm_call")) | group_by(.task)
       | map({task: .[0].task, calls: length, tokens_in: (map(.tokens_in) | add), tokens_out: (map(.tokens_out) | add)})' logs/mnogobase.jsonl

# какие сущности слились и как
jq -c 'select(.event=="entity_merged") | {name, into, score, method}' logs/mnogobase.jsonl

# один прогон (run_id печатается в конце ingest)
jq -c 'select(.run_id=="<run_id>")' logs/mnogobase.jsonl
```

## 5. Как это устроено внутри

### 5.1 Конвейер ingest

Схема показывает путь каждого файла через этапы: подготовка, обнаружение, при необходимости удаление старой версии, пять этапов и сборка wiki.

```mermaid
flowchart TD
    PREP["prepare: проверка эмбеддера,<br/>коллекции и схема, running в pending"] --> FIN["доделать незавершённые удаления"]
    FIN --> DISC["discover: обход путей,<br/>фильтр расширений, doc_id"]
    DISC --> KNOWN{"что с файлом?"}
    KNOWN -->|"все этапы done"| SKIP["skipped; после переименования<br/>ссылки на новый путь"]
    KNOWN -->|"путь известен, содержимое новое"| RM["удалить старую версию<br/>через журнал pending_removals"]
    KNOWN -->|"есть failed, нет флага"| FAILED["failed: нужен --retry-failed"]
    KNOWN -->|"новый или незавершённый"| NEXT["первый этап не в done"]
    RM --> NEXT
    NEXT --> PARSE["parse: Docling"]
    PARSE --> CHUNK["chunk: HybridChunker"]
    CHUNK --> EMBED["embed: Qdrant mb_chunks,<br/>Document и Chunk в Neo4j"]
    EMBED --> EXTRACT["extract: LLM по чанкам,<br/>extraction_cache"]
    EXTRACT --> GRAPH["graph: слияние сущностей,<br/>MENTIONS, RELATED, dirty"]
    GRAPH --> WIKIQ{"--no-wiki?"}
    WIKIQ -->|"нет"| WB["wiki build"]
    WIKIQ -->|"да"| LATER["wiki build позже"]
```

Детали этапов:

- **parse** — `DocumentConverter` с OCR из `parsing.ocr` / `parsing.ocr_lang` и ускорителем из `device` (эти опции заданы для PDF и картинок; на CUDA увеличены размеры батчей). При `vision.enabled` картинки PDF, DOCX и PPTX описывает VLM (раздел [7.16](#716-картинки-и-графики-vision)), а файл-картинка описывается ещё и целиком. Заголовок документа — первый элемент Docling с меткой `TITLE`, иначе имя файла. Файл больше `parsing.max_file_mb` или `parsing.max_pages` стадия отклоняет сразу (`ParseLimitError`). Файл-картинка перед VLM уменьшается до 2048 px по длинной стороне. Картинки хранятся один раз — PNG в `cache/<doc_id>/images/`; в JSON разбора их пиксели не дублируются.
- **chunk** — `HybridChunker(merge_peers=True)` с токенайзером из `chunking.tokenizer` (`chunking/tokenizer.py`) и пределом `chunking.max_tokens`. При `auto` это `POST /tokenize` сервера эмбеддера (llama.cpp, локальный или внешний с `serve: api`) (`ServerTokenizer` с кэшем): токенайзер зашит в GGUF, исходный HF-репозиторий не нужен (число токенов совпадает с HF-токенайзером, проверено на Qwen3-Embedding-0.6B); если у сервера нет `/tokenize`, укажите HF-репозиторий в `chunking.tokenizer`. Для эмбеддинга используется `contextualize(chunk)` (заголовки раздела и текст), в payload и граф кладётся чистый текст, заголовки и страницы. Пустые чанки отбрасываются.
- **embed** — плотные векторы батчами по `embedder.batch_size` через `POST /embeddings` OpenAI-совместимого сервера, обрезка до `embedder.dim` (при `auto` — без обрезки) и нормировка; BM25 через fastembed. Шаблон задаёт `embedder.doc_template`; в текущем конфиге это `{text}`, где текст чанка уже дополнен заголовками раздела через `contextualize`.
- **extract** — для каждого чанка промпт `extract.md` и строгая JSON Schema `{entities: [{name, type, description, aliases}], relations: [{source, target, predicate, description, strength}]}`. Измерения, координаты, даты и безымянные гипотетические объекты («ring at 144 au», «an unseen planet») промпт просит не делать сущностями. Ответ чистится: неизвестный тип → `Other`, дубли имён сливаются, предикат → `snake_case`, `strength` ограничивается 1–10, связи с неизвестными концами отбрасываются. Результат кэшируется по `(chunk_id, prompt_version, model)`.
- **graph** — по каждому чанку: слияние каждой сущности (раздел 5.5), `MENTIONS` от чанка к сущностям, `entity_ids` в payload чанка, `RELATED` по `(src, dst, predicate)` с дописыванием `evidence` и `weight += strength`. Все затронутые сущности попадают в `dirty_entities`. Если у документа больше `max_failed_ratio` чанков без кэша извлечения, `graph` падает, а `extract` возвращается в `pending`.

### 5.3 Состояния этапов

Каждый этап каждого документа хранится в таблице `stages` со статусом; диаграмма показывает переходы, включая возобновление после прерывания и повтор упавших.

```mermaid
stateDiagram-v2
    direction LR
    [*] --> pending
    pending --> running : старт этапа
    running --> done : успех
    running --> failed : ошибка
    running --> pending : прерван
    failed --> running : retry-failed
    done --> pending : нет кэша extract
    done --> [*]
```

- Статуса нет в таблице → этап считается `pending`. Документ без незавершённых этапов пропускается (`skipped`).
- Этап в `running` при старте следующего `ingest` значит, что процесс прервали: он сбрасывается в `pending` (событие `resuming_interrupted_stages`), и работа продолжается с него.
- `failed` без `--retry-failed` не перезапускается: файл помечается `failed` с подсказкой. С флагом документ продолжается с первого не-`done` этапа; на `extract` повторно вызываются только чанки без кэша.
- Статус файла (`files.status`): `processing` во время работы, затем `done` или `failed`; `pending` — если файл нужно загрузить заново после удаления общей с ним старой версии.

### 5.4 Модель данных

**Neo4j.** Узлы и связи с ключевыми свойствами:

```mermaid
erDiagram
    Document ||--o{ Chunk : HAS_CHUNK
    Chunk |o--o| Chunk : NEXT
    Chunk }o--o{ Entity : MENTIONS
    Entity }o--o{ Entity : RELATED
    WikiPage |o--|| Entity : ABOUT
    WikiPage }o--o{ WikiPage : LINKS_TO
    WikiPage }o--o{ Chunk : CITES
    Document {
        string doc_id PK
        string path
        string title
        string mime
        int n_pages
        datetime ingested_at
    }
    Chunk {
        string chunk_id PK
        string doc_id
        int idx
        string text
        list headings
        int page_start
        int page_end
        int n_tokens
        string modality
    }
    Entity {
        string entity_id PK
        string name
        string type
        list aliases
        string aliases_text
        string description
        list descriptions
        int mention_count
    }
    WikiPage {
        string page_id PK
        string slug
        string title
        string path
        string content_hash
        int version
        datetime updated_at
    }
```

- `RELATED` — один тип связи, смысл в свойствах: `predicate` (snake_case), `description` (самое длинное из описаний), `weight` (сумма `strengths`), `evidence` (список `chunk_id`), `strengths` (сила из каждого чанка, параллельно `evidence`).
- `Entity.mention_count` — число чанков с `MENTIONS` на сущность; `descriptions` — накопленные описания, `description` — их склейка; `aliases_text` — алиасы через ` | ` для полнотекстового индекса.
- `WikiPage.page_id` равен `entity_id`, `path` — путь относительно `wiki/` (`entities/<slug>.md`).
- Ограничения уникальности: `Document.doc_id`, `Chunk.chunk_id`, `Entity.entity_id`, `WikiPage.page_id`. Индексы: `WikiPage.slug`, `Chunk.doc_id`, полнотекстовый `entity_names` по `Entity.name` и `Entity.aliases_text`. Схема создаётся `IF NOT EXISTS` при каждом запуске (`GraphStore.ensure_schema`).

**Qdrant.** Префикс коллекций — `qdrant.prefix` (`mb_`). Плотный вектор называется `dense` (косинус, размерность `embedder.dim` или, при `auto`, модели), разреженный — `bm25` (модификатор IDF). Все индексируемые поля payload — keyword.

| Коллекция | Векторы | Индексы payload | Что эмбеддится | ID точки |
|---|---|---|---|---|
| `mb_chunks` | `dense`, `bm25` | `chunk_id`, `doc_id`, `entity_ids`, `modality` | заголовки раздела и текст чанка | `uuid5(chunk_id)` |
| `mb_entities` | `dense` | `entity_id`, `type`, `name_keys` | `"{name}: {description}"` | `uuid5(entity_id)` |
| `mb_wiki_pages` | `dense`, `bm25` | `page_id`, `entity_id` | раздел страницы без сносок, с заголовком `Название — Раздел` | `uuid5("{page_id}#{номер раздела}")` |

**Детерминированные ID** (`src/mnogobase/ids.py`) — на них держатся идемпотентность и дедупликация:

| Объект | ID |
|---|---|
| Документ | `doc_id = sha256(байты файла)[:16]` — одинаковое содержимое по разным путям даёт один документ |
| Чанк | `chunk_id = f"{doc_id}:{idx:05d}"` |
| Сущность | `entity_id = sha1(f"{type.casefold()}\|{normalize_name(name)}")[:16]`; `normalize_name`: NFKC, casefold, все разделители кроме `+` и `#` → пробел, пробелы схлопываются |
| Wiki-страница | `page_id = entity_id`; `slug` = нормализованное имя через дефис (`#` → `sharp`, длинные имена обрезаются с хешем), при занятости `slug-<тип>`, затем `slug-<6 символов id>` |
| Точка Qdrant | `uuid5(NAMESPACE, ключ)`, ключ — `chunk_id`, `entity_id` или `page_id#i` |

**Registry PostgreSQL** (схема `mnogobase_project_default`, то есть `<database.schema_prefix>_project_<database.project>`):

| Таблица | Колонки | Зачем |
|---|---|---|
| `files` | `path` PK, `doc_id`, `size`, `mtime`, `status`, `updated_at` | какие пути загружены и с каким содержимым |
| `stages` | `doc_id`, `stage`, `status`, `attempts`, `error`, `updated_at` | состояние этапов `parse`, `chunk`, `embed`, `extract`, `graph` |
| `extraction_cache` | `chunk_id`, `prompt_version`, `model`, `result_json` | кэш ответов LLM на этапе `extract` |
| `dirty_entities` | `entity_id` PK, `marked_at` | очередь сущностей на обновление wiki |
| `meta` | `key` PK, `value` | подпись эмбеддера индекса (`embedder` = `<serve>:<веса>:<dim>:tpl-<хеш шаблонов>`, например `llamacpp:Qwen/Qwen3-Embedding-4B-GGUF:Q4_K_M:2560:tpl-...`) и служебные значения |
| `pending_removals` | `doc_id` PK, `plan_json` | журнал незавершённых удалений старых версий документов |

В той же схеме лежат остальные таблицы проекта: очередь `jobs` (с `desired`, `write_state`, `worker_heartbeat`), `uploads` (файлы, загруженные через API), `users`, `sessions`, `conversations`, `messages` (раздел 16), `llm_usage` (учёт вызовов LLM) и служебная `schema_migrations`.

### 5.5 Слияние сущностей (entity resolution)

Каждая извлечённая сущность либо совпадает с уже известной, либо сливается с похожей, либо создаётся заново:

```mermaid
flowchart TD
    IN["сущность из extract:<br/>name, type, description, aliases"] --> ID["entity_id из type и name"]
    ID --> EXISTS{"такой entity_id<br/>уже есть в Neo4j?"}
    EXISTS -->|"да"| MERGE["слить: aliases, descriptions"]
    EXISTS -->|"нет"| SEARCH["кандидаты из mb_entities:<br/>до 3 с тем же ключом имени или алиаса,<br/>затем top 3 с косинусом не ниже llm_check 0.75"]
    SEARCH --> CAND{"следующий кандидат?"}
    CAND -->|"нет"| NEW["новая сущность"]
    CAND -->|"score ≥ auto_merge 1.0"| MERGE
    CAND -->|"остальные"| SAME{"LLM resolve_same:<br/>одна и та же?"}
    SAME -->|"да"| MERGE
    SAME -->|"нет"| CAND
    MERGE --> MANY{"описаний больше<br/>max_descriptions 5?"}
    MANY -->|"да"| SUMM["LLM resolve_summarize<br/>сжимает в одно"]
    MANY -->|"нет"| SAVE["если что-то изменилось:<br/>вектор, Qdrant, затем Neo4j"]
    SUMM --> SAVE
    NEW --> SAVE
```

- Имена извлекаются как канонические английские, исходное написание уходит в `aliases` — поэтому русский и английский тексты обычно дают один `entity_id` сразу, а вектор и LLM ловят остальные случаи (синонимы, сокращения, варианты написания).
- При слиянии сохраняются имя и тип существующей сущности, новое имя становится алиасом. Сопоставление `entity_id` извлечённой сущности с итоговым запоминается на время процесса, чтобы не искать заново.
- Поиск идёт без фильтра по типу. Ключ имени — `normalize_name` без пробелов (`MagAO-X` = `MagAOX`, `Semi-major axis` = `Semimajor axis`); он считается от имени и всех алиасов и хранится в payload `name_keys`. Кандидаты по ключу проверяются LLM при любом косинусе: одна сущность под другим типом или с другим описанием (`Sun` как Location и как Other, `NASA` и `National Aeronautics and Space Administration`) часто даёт косинус 0.5–0.75.
- По умолчанию сущности не сливаются по одному косинусу (`auto_merge: 1.0`), см. раздел 7.12.

### 5.6 Инкрементальное обновление wiki

Сборка wiki обрабатывает только сущности из очереди `dirty_entities` (или все при `--all`):

```mermaid
flowchart TD
    DIRTY["dirty_entities"] --> ELIG{"mention_count ≥ min_mentions?"}
    ELIG -->|"нет, но страница есть"| DROP["удалить страницу,<br/>ссылающиеся страницы в dirty"]
    ELIG -->|"да"| EVID["evidence: до evidence_k чанков,<br/>упоминающих сущность"]
    EVID -->|"ни одного"| SKIPPED["skipped"]
    EVID --> SLUG["slug: новый или прежний"]
    SLUG --> DRAFT["LLM wiki_page.md: факты, связи,<br/>evidence, текущий текст страницы"]
    DRAFT --> VALID["цитаты только из evidence,<br/>ссылки только на существующие страницы"]
    VALID --> WRITE["entities/slug.md:<br/>frontmatter, Related, Sources"]
    WRITE --> INDEX["разделы в mb_wiki_pages,<br/>WikiPage, ABOUT, LINKS_TO, CITES"]
    INDEX --> CLEAR["очистить dirty, кроме упавших"]
    DROP --> CLEAR
    CLEAR --> FILES["index.md заново,<br/>запись в log.md"]
```

- **Evidence** — чанки, где упомянута сущность (фильтр `entity_ids` в `mb_chunks`), ранжированные по близости к вектору `"{name}: {description}"`, не больше `wiki.evidence_k` (12). При обновлении к ним добавляются чанки, которые уже цитирует текущая страница, если они существуют и всё ещё упоминают сущность: валидные цитаты не теряются, когда чанк выпал из свежего top-K.
- **Обновление, а не переписывание.** LLM получает текущий текст страницы и правило «сохранить подтверждённое, добавить новое, исправить противоречия».
- **Валидация.** Сноски `[^id]` на чанки вне evidence удаляются. `[[Name]]` превращается в `[[slug|Name]]`, только если у Name (по имени или алиасу) есть страница или она пишется в этом же прогоне, иначе остаётся текстом. Разделы `## Related` и `## Sources`, заголовок и определения сносок генерируются кодом, а не LLM.
- **Надёжность.** Ошибка одной страницы не валит сборку: сущность остаётся в очереди и повторяется в следующий раз. Узел страницы и её рёбра (`ABOUT`, `LINKS_TO`, `CITES`) пишутся одной транзакцией. `index.md` пересобирается целиком, в `log.md` дописывается запись, если что-то изменилось или были обработаны документы; когда `log.md` больше 1 МБ, он переименовывается в `log.1.md` и журнал начинается заново.
- **Устаревшие страницы.** Удаление или изменение документа инвалидирует страницы затронутых сущностей до LLM-вызовов: файл и разделы в Qdrant удаляются, а узел `WikiPage` помечается `stale` (slug и входящие ссылки сохраняются). Такой страницы нет в `index.md`, в `reindex` и в API, пока `wiki build` её не пересоберёт; если у сущности не осталось подтверждений, узел удаляется, а ссылающиеся страницы ставятся в очередь на пересборку.

### 5.7 Поиск и ответ

Четыре режима собирают контекст по-разному, а ответ формирует общий `Answerer`:

```mermaid
flowchart TD
    Q["Вопрос + перевод на английский<br/>если включён retrieval.translate"]
    Q --> RAG["rag · Qdrant mb_chunks<br/>dense + BM25 → RRF"]
    RAG --> RERANK["Реранкер → top k → соседи<br/>при включённых настройках"]
    Q --> WIKI["wiki · Qdrant mb_wiki_pages<br/>dense + BM25 → разделы страниц"]
    WIKI --> WCTX["Разделы + цитируемые чанки<br/>доказательства из Neo4j"]
    Q --> SEEDS["graph · стартовые сущности<br/>Qdrant mb_entities + Neo4j fulltext"]
    SEEDS --> HOPS["Neo4j · окрестность RELATED<br/>сущности, тройки и чанки-доказательства"]
    RERANK --> SELECT["Контекст выбранного режима<br/>all: три ветки, доли бюджета, без повторов"]
    WCTX --> SELECT
    HOPS --> SELECT
    SELECT --> ANS["Answerer<br/>бюджет контекста · нумерация источников"]
    ANS --> PROMPT["LLM · answer.md"]
    PROMPT --> OUT["Ответ с номерами цитат<br/>+ таблица источников"]

    classDef rag fill:#ecfdf5,stroke:#059669,color:#064e3b
    classDef wiki fill:#fff7ed,stroke:#ea580c,color:#7c2d12
    classDef graphLayer fill:#f5f3ff,stroke:#7c3aed,color:#3b0764
    classDef shared fill:#eff6ff,stroke:#2563eb,color:#172554
    class RAG,RERANK rag
    class WIKI,WCTX wiki

```

- **Перевод запроса.** Если вопрос не на английском и `retrieval.translate: true`, `QueryTranslator` (`retrieval/translate.py`, промпт `translate_query.md`, задача `query`) один раз переводит его на английский; все режимы ищут и по оригиналу, и по переводу (`alt_queries`). Источники, wiki и имена сущностей в основном английские, а BM25 не сопоставляет русский запрос с английским текстом. Ошибка перевода не прерывает ответ: поиск идёт по оригиналу.
- **rag** — гибридный запрос Qdrant: по два prefetch по `k * 4` (`dense` и `bm25`) на каждую формулировку, слияние RRF, `k` результатов. Текст каждого чанка начинается с пути заголовков (`Глава > Раздел`). При `retrieval.neighbors: N > 0` попадание расширяется до N соседних чанков с каждой стороны, пока у них те же заголовки (тот же раздел); попадание, уже вошедшее в окно более сильного, пропускается. Цитата указывает на чанк-попадание.
- **Реранкер** (`rerank.enabled`, `retrieval/rerank.py`). В режиме rag гибридный поиск отдаёт `rerank.candidates` попаданий, Qwen3-Reranker оценивает каждое (путь заголовков + текст) против исходного вопроса, и остаются лучшие `k`; `ContextItem.score` — оценка реранкера (0–1). Все кандидаты уходят одним запросом `POST /rerank` (формат Jina/Cohere), промпт Qwen3-Reranker строит сервер: llama.cpp — из GGUF. Если реранкер недоступен, в лог пишется `rerank_failed` и используется порядок гибридного поиска.
- **wiki** — то же по разделам wiki; после каждого раздела идут чанки из его `chunk_ids` (всего не больше `k`), чтобы ответ ссылался на файл и страницу.
- **graph** — seeds: до `graph.seeds` сущностей по вектору вопроса с косинусом не ниже `graph.seed_threshold` плюс полнотекстовый поиск по именам и алиасам, по каждой формулировке вопроса (всего не больше `2 * seeds`; векторные seeds — по убыванию сходства). Окрестность на `graph.hops` шагов (в коде ограничено 1–3), до `graph.max_relations` связей; контекст — описания seed-сущностей, тройки `A —predicate→ B` и до `k` чанков-доказательств.
- **all** — режимы по очереди заполняют свою долю `retrieval.context_tokens` (`retrieval.budget`), повторы по `(kind, ref)` пропускаются.
- **Answerer** нумерует элементы `[1]..[n]`, пока не исчерпан `retrieval.context_tokens` (первый элемент берётся всегда; токены оцениваются как символы / 4), отправляет промпт `answer.md` и отмечает `cited` у источников, номера которых встречаются в ответе.

На схеме показаны возможные ветки: `ask -m rag/wiki/graph` выполняет выбранную, `all` объединяет три. Наличие номера цитаты означает, что модель сослалась на источник; соответствие утверждения источнику отдельно оценивается метриками и ручной проверкой.

### 5.8 APOC и GDS

**Что это даёт пользователю.** APOC — библиотека процедур Neo4j: в нашем поиске она управляет обходом связей вокруг найденных сущностей. Собственной численной оценки APOC в этом режиме не вычисляет. GDS (Graph Data Science) — библиотека графовых алгоритмов: PageRank оценивает центральность сущностей, Leiden объединяет их в сообщества по структуре связей.

| Результат | Как понимать | Где посмотреть |
|---|---|---|
| `pagerank` | насколько сущность центральна в анализируемом графе; больше — выше центральность. Это не вероятность правильного ответа и не процент качества. Сравнивайте сущности внутри одного снимка анализа | `graph status`, поле `entities`; полный рейтинг — через Neo4j Browser ниже |
| `community` | ключ сообщества вида `community:…`; одинаковый ключ означает принадлежность к одной группе. Это не название темы и не оценка качества группы | `graph status`; состав и размеры сообществ — через Browser |
| `ready` | `true` — есть опубликованный актуальный снимок; `false` — снимка нет или он сброшен после изменения данных | `graph status` |
| `completed_at` | время последнего успешного анализа; при `ready: false` прежнее время само по себе не означает актуальность | `graph status` |
| `metadata.nodes`, `relationships`, `communities` | число сущностей, исходных связей и сообществ в последнем расчёте. При `ready: false` это могут быть исторические значения | `graph status` |

APOC позволяет обходить `RELATED` в ширину: в проектном `config.yaml` включён `graph.traversal: apoc`. Глубина ограничена тремя шагами, список разрешённых узлов — только Entity текущего проекта. При превышении `graph.analysis.apoc_max_nodes` или отсутствии процедуры выполняется обычный Cypher-обход. Для самого APOC-запроса задан таймаут; ошибки соединения и прочие ошибки сервера не маскируются. Оба варианта возвращают исходные `evidence` и чанки для цитирования.

**Как пользоваться.** Из корня уже проиндексированного проекта выполните оценку памяти, затем анализ и просмотр результата. GDS запускается отдельно, без эмбеддера, Qdrant и LLM:

```bash
uv run mnogobase graph analyze --estimate  # оценить память проекции, без её создания
uv run mnogobase graph analyze             # PageRank + Leiden, сохранить результат
uv run mnogobase graph status              # актуальность, версии, топ сущностей и их сообщества
uv run mnogobase graph clear --yes         # очистить только производную аналитику
```

В полном стеке те же команды запускаются в контейнере: `docker compose exec api mnogobase graph analyze`.

Команды требуют существующий проект. `analyze` и `clear` используют общую блокировку GDS и существующую блокировку писателя корпуса. Проекция включает только Entity и RELATED проекта, как взвешенный ненаправленный граф. PageRank оценивает структурную центральность, Leiden — сообщества; числовые номера сообществ заменяются хешами их состава. Поле `community` у сущности в `status` позволяет увидеть её группу; вывод ограничен 20 центральными сущностями.

**Как читать оценки.** `graph status` печатает JSON. Ниже сокращённый учебный пример; имена, числа и ключи иллюстративные:

```json
{
  "ready": true,
  "completed_at": "2026-11-02T20:00:00Z",
  "metadata": {
    "nodes": 12,
    "relationships": 18,
    "communities": 3
  },
  "entities": [
    {
      "entity_id": "example-transformer",
      "name": "Transformer",
      "pagerank": 2.31,
      "community": "community:0a1b2c3d4e5f678901234567"
    },
    {
      "entity_id": "example-attention",
      "name": "Attention",
      "pagerank": 1.42,
      "community": "community:0a1b2c3d4e5f678901234567"
    }
  ]
}
```

В примере Transformer центральнее Attention; обе сущности попали в одно сообщество. По этим числам нельзя заключить, что сведения о Transformer точнее или полезнее для любого вопроса. CLI показывает только топ-20, поэтому отсутствие сущности в списке не означает, что её нет в графе или что она не получила оценку. Версии плагинов в `metadata.plugins` относятся к последнему расчёту; текущие установленные версии проверяет `uv run mnogobase doctor`.

**Как посмотреть больше в Neo4j Browser.** Откройте http://localhost:7474 и подключитесь к базе, как в разделе 4.1 (в режиме разработки; в полном стеке порт Neo4j не публикуется). Запросы используют labels `Entity` и `AnalysisState`.

Топ-100 сущностей с оценками:

```cypher
MATCH (s:AnalysisState {key: 'graph'})
WHERE s.run_id IS NOT NULL
MATCH (e:Entity)
WHERE e.analytics_run_id = s.run_id
RETURN e.entity_id AS entity_id, e.name AS name,
       e.analytics_pagerank AS pagerank, e.analytics_community AS community
ORDER BY pagerank DESC, entity_id
LIMIT 100;
```

Крупнейшие сообщества, их размеры и примеры участников:

```cypher
MATCH (s:AnalysisState {key: 'graph'})
WHERE s.run_id IS NOT NULL
MATCH (e:Entity)
WHERE e.analytics_run_id = s.run_id
RETURN e.analytics_community AS community, count(*) AS members,
       collect(e.name)[..10] AS examples
ORDER BY members DESC, community
LIMIT 20;
```

Участники конкретного сообщества — замените ключ в кавычках значением из предыдущего запроса:

```cypher
MATCH (s:AnalysisState {key: 'graph'})
WHERE s.run_id IS NOT NULL
MATCH (e:Entity)
WHERE e.analytics_run_id = s.run_id
  AND e.analytics_community = 'community:0a1b2c3d4e5f678901234567'
RETURN e.entity_id AS entity_id, e.name AS name, e.analytics_pagerank AS pagerank
ORDER BY pagerank DESC, entity_id
LIMIT 100;
```

Эти запросы сверяют оценки с опубликованным снимком. Если результат пуст и `ready: false`, повторите `graph analyze`: у отдельных узлов после изменения корпуса могут оставаться старые свойства аналитики, но поиск их не использует. `graph clear --yes` удаляет производные оценки и временные проекции проекта; документы, связи, wiki и векторы остаются.

**Как оценки влияют на ответ.** Чтобы использовать графовый поиск, выполните `uv run mnogobase ask "Ваш вопрос" -m graph` или `-m all`. Для ответа нужны настроенные серверы моделей/API, как и до подключения GDS.

В `graph`/`all` при `graph.use_gds: true` готовый PageRank разрывает равенство весов **уже найденных** связей по сумме оценок концов. Он не добавляет кандидатов вне окрестности и не доказывает истинность утверждения. Если снимка нет или он устарел, сохраняется исходный порядок. Изменения документов, чанков, сущностей, упоминаний и связей, а также удаление документа инвалидируют анализ в той же Neo4j-транзакции. Публикация нового снимка атомарна и проверяет ревизию исходного графа. Алгоритмы не запускаются при `ask`; после изменений корпуса повторите `graph analyze`.

**Как Leiden помогает генерации.** В проекте включён `graph.community.enabled: true`.
После поиска стартовых сущностей `GraphRetriever` выбирает их сообщества из актуального
анализа и добирает исходные чанки, упоминающие участников этих групп. Так LLM получает
сведения за пределами обычного `graph.hops`, а цитаты продолжают вести к документам и
страницам. Одинаковое сообщество означает структурную близость, поэтому дополнительный
фрагмент может оказаться менее полезным для конкретного вопроса; центральность не заменяет
проверку фактов по тексту источника.

По умолчанию берутся до 3 сообществ по порядку стартовых сущностей, до 30 участников
каждого по PageRank и до 3 дополнительных чанков. Внутри сообщества чанки упорядочены по
числу найденных участников и их центральности; повторы исключаются. Общий лимит исходных
чанков остаётся `retrieval.k`: если есть локальные подтверждения связей, расширению
доступно не больше половины этого лимита, остальные места заполняются локальными.
При `k=1` и локальном подтверждении дополнительного чанка не будет. Если связей нет,
актуальное сообщество всё равно может дать исходный текст через упоминания сущностей.
При добавлении таких источников чанки идут перед описаниями сущностей и связей, чтобы
они имели приоритет в контекстном бюджете.

Запрос ограничен `graph.community.timeout_s` (5 секунд). При его таймауте или отсутствии
актуального анализа остаётся обычный графовый контекст. В логах событие `leiden_context`
показывает число добавленных чанков; `leiden_context_timeout` означает пропуск расширения.
Источники ответа содержат путь и страницу исходного фрагмента. В режиме `all` дополнительно
действует общий бюджет графовой части, поэтому не каждый найденный чанк попадёт в prompt.

Чтобы отключить только расширение сообществ, установите `graph.community.enabled: false`.
`graph.use_gds: false` отключает и PageRank, и Leiden при поиске; для обычного Cypher-обхода
также задайте `graph.traversal: cypher`. Переиндексация не нужна.

Leiden не пишет текст самостоятельно: готовые группы помогают собрать контекст, после
чего настроенная LLM генерирует ответ. Дополнительных LLM-вызовов для сводок здесь нет.
Обзоры сообществ для глобальных вопросов остаются отдельным возможным расширением —
см. [GraphRAG Global Search](https://microsoft.github.io/graphrag/query/global_search/).

Начальные лимиты: 100 000 узлов, 500 000 исходных рёбер, 1536 МиБ оценки памяти GDS, 120 секунд на запрос. Перед проекцией проверяется её оценка памяти, после создания — оценки алгоритмов; учитываются проекция и наибольшая рабочая память последовательных алгоритмов. При исключении временная проекция удаляется; после аварийного завершения её убирает следующий `graph analyze` или `graph clear`. Оценки памяти не гарантируют защиту от OOM.

`doctor` отдельно проверяет версии APOC/GDS и необходимые процедуры (`graph_plugins`); отсутствие плагинов даёт предупреждение, обычные режимы остаются доступны. `graph analyze` требует GDS и сообщает ошибку при его отсутствии. HTTP healthcheck контейнера не проверяет загрузку плагинов. В `compose.yaml` версии закреплены: APOC входит в образ, а jar GDS заранее кладёт `deploy/prepare-data.sh` в `MB_DATA/neo4j-plugins` с проверкой sha256, без скачивания при старте.

Автоматические wiki-обзоры сообществ — отдельный будущий этап; текущая реализация аналитики дополнительных LLM-запросов не делает.

### 5.9 Гарантии согласованности

- **Идемпотентность.** Все записи — upsert/`MERGE` по детерминированным ID, поэтому повтор этапа после падения даёт тот же результат. `merge_relation` не добавляет `evidence` из того же чанка дважды (вес не удваивается), `mention_count` пересчитывается подсчётом связей.
- **Порядок записи.** Этап отмечается `done` только после всех записей. На `embed`: узел `Document` → точки Qdrant → узлы `Chunk`. При слиянии сущности: вектор → Qdrant → Neo4j, чтобы сбой эмбеддера или Qdrant не оставил граф «впереди». На `graph`: сначала `entity_ids` чанка в Qdrant, затем его упоминания и связи в Neo4j одной транзакцией на чанк.
- **Кэш чанков** (`<doc_id>.chunks.json`) пишется во временный файл и переименовывается, поэтому сбой не оставит его обрезанным; нечитаемый кэш восстанавливается из узлов `Chunk` в Neo4j и записывается заново.
- **Изменённый файл.** План удаления старой версии вычисляется только чтением и записывается в журнал `pending_removals`. Затем: одна транзакция Neo4j (чанки, документ, `evidence` из его чанков, связи без `evidence`, сущности без упоминаний и их страницы) → очередь wiki → Qdrant и файлы wiki → registry → запись журнала удаляется последней. Граф чистится первым намеренно: если шаг Qdrant не удался, режимы `rag`/`wiki`/`all` до следующего `ingest` или `wiki build` (они доводят журнал) могут вернуть текст удалённой версии, режим `graph` уже чист. Незавершённое удаление перепроверяется по графу, а если довести его не удаётся, `ingest` и `wiki build` завершаются с кодом 2.
- **Одинаковое содержимое по двум путям** — один документ. Второй путь пропускается; изменение одного из файлов не удаляет данные, пока другой путь хранит то же содержимое (ссылки в источниках переводятся на живой путь). Живой путь — тот, где файл существует и его хеш совпадает с `doc_id`: строка registry для переименованного или удалённого файла копией не считается.
- **Переименование.** Файл с новым путём и прежним содержимым пропускается, а если записанный путь документа (кэш чанков или `Document.path` в Neo4j; кэша может не быть) больше не хранит это содержимое, документ переводится на новый путь: сначала `path` в payload чанков Qdrant, затем `Document.path`, кэш чанков последним, поэтому прерванный перевод доделывает следующий `ingest`. Wiki-страницы, которые цитируют чанки документа, помечаются на обновление: раздел `## Sources` получит новое имя файла при ближайшей сборке wiki. Строки registry с этим содержимым, файла которых больше нет, удаляются, а строки существующих файлов (копий или изменённых) остаются. Если после этого `ingest` изменить переименованный файл, старая версия удаляется как обычно. Переименование и правка между двумя запусками `ingest` выглядят как удалённый старый файл плюс новый: старая версия остаётся (см. ограничения).
- **Блокировка.** PostgreSQL advisory lock корпуса не даёт параллельно запускать пишущие команды; соединение удерживается на всё время операции.
- **Повторы сетевых вызовов.** LLM: до 5 попыток при ошибках соединения и таймаутах, 429 и 5xx (экспоненциальная пауза до 30 с), всего не дольше `llm.retry_deadline_s` (900 с); невалидный JSON — ещё до 2 попыток с текстом ошибки валидации. В повтор передаются исходные сообщения, первые 2000 символов последнего невалидного ответа и его ошибка; длинные ответы и история предыдущих исправлений не накапливаются. Эмбеддер и реранкер: до 5 попыток при сетевых ошибках и 5xx. Qdrant: до 5 попыток при сетевых ошибках. Neo4j — средствами драйвера.
- **Подпись эмбеддера.** В `meta` хранится `model_id:dim:tpl-<хеш>`, где хеш (8 hex-символов sha256) покрывает `embedder.doc_template` и `query_template`. Смена модели, размерности или любого из шаблонов останавливает `ingest`, `wiki build`, `ask` и `compare` до `reindex`. Старая подпись без хеша (`model_id:dim`) принимается, если модель и размерность совпадают, и переписывается в новом формате при следующем запуске (только если значение в `meta` не изменилось за это время: идущий параллельно `reindex` не затирается). Такая подпись не знает, какими шаблонами построен индекс: если вы меняли `doc_template`/`query_template` до этой версии и не запускали после этого `reindex`, выполните `uv run mnogobase reindex` один раз.
- **Ограничения.** Удалённые с диска файлы из индекса не убираются (строки registry для них остаются, если то же содержимое не нашлось по другому пути). Также остаётся старая версия файла, который переименовали и изменили без `ingest` между этими шагами.

## 6. Справочник настроек

Все несекретные параметры — в `config.yaml`, секреты — в `.env`. Описание всех полей с типами и границами — в `src/mnogobase/config.py`; значения по умолчанию в коде местами отличаются от поставляемого `config.yaml` (раздел [2.6](#26-что-задано-в-configyaml)).

Приоритет источников: переменные `MNOGOBASE_*` (в том числе из `.env`) → файл конфига → значения по умолчанию. Конфиг проверяется строго: ошибка (неверный YAML, неизвестный ключ — опечатка в `config.yaml` или во вложенной переменной вроде `MNOGOBASE_LLM__MODLE`, значение вне допустимых границ, неизвестное значение, некорректный тип сущности, неверные доли `retrieval.budget`) останавливает любую команду с `Invalid configuration: ...` и кодом 2; явно указанный, но отсутствующий файл — `Config file not found: ...`. Относительные пути (`data_dir`, `logs_dir`, `runs_dir`, `wiki.dir`) считаются от текущей папки, а не от файла конфига.

### 6.2 Переопределение через переменные окружения

Любой ключ можно задать переменной с префиксом `MNOGOBASE_`, вложенность — через `__`. Переменные можно положить и в `.env`.

```bash
MNOGOBASE_LLM__MODEL=gpt-6-luna-mini uv run mnogobase ask "..."
MNOGOBASE_EMBEDDER__BASE_URL=http://gpu-host:8001/v1   # сервер роли на другой машине
MNOGOBASE_EMBEDDER__DIM=512
MNOGOBASE_LLM__OVERRIDES__ANSWER=gpt-6-luna
MNOGOBASE_RETRIEVAL__BUDGET__RAG=0.5            # остальные доли берутся из config.yaml
MNOGOBASE_PARSING__EXTENSIONS='["pdf", "md"]'   # списки и словари — в JSON
MNOGOBASE_CONFIG=other.yaml                     # другой файл конфига (как --config)
```

Типы сущностей из переменной задаются **JSON-объектом или JSON-списком** и **заменяют** набор из YAML целиком, а не дополняют его:

```bash
MNOGOBASE_EXTRACT__ENTITY_TYPES='{"Gene": "A named gene or protein.", "Other": "Anything else."}'
MNOGOBASE_EXTRACT__ENTITY_TYPES='["Gene", "Condition", "Other"]'
```

Значение не в JSON (например, `Person,Other`) — ошибка конфига с кодом 2. Опечатка в ключе внутри секции (`MNOGOBASE_LLM__MODLE`) тоже ошибка (`Extra inputs are not permitted`); переменная с неизвестной секцией верхнего уровня (`MNOGOBASE_FOO`) игнорируется.

### 6.3 Типы сущностей

Типы задаются в `extract.entity_types`: имя типа → одна строка описания. Описания попадают в промпт извлечения и помогают LLM различать похожие типы. По умолчанию 18 крупных типов для документов из любых областей:

`Person`, `Organization`, `Location`, `Event`, `Project`, `Product`, `Equipment`, `Software`, `Technology`, `Method`, `Concept`, `Work`, `Metric`, `Regulation`, `Substance`, `Condition`, `Organism`, `Other`.

Набор нарочно небольшой. Тип входит в `entity_id`, поэтому каждая размытая граница между типами даёт дубли (одна сущность под двумя типами), а поиск по типу не фильтрует — тип нужен для подписи в режиме graph, frontmatter wiki и цветов. Близкие типы объединены: обученные модели — `Software`, дисциплины и природные процессы — `Concept`, датасеты и журналы — `Work`, небесные тела — `Location`, эпохи — `Event`. Узкие типы под свой корпус (`Gene`, `Contract`, `Vulnerability`, …) добавляйте в `config.yaml`.

Чтобы добавить или изменить тип, отредактируйте список в `config.yaml` (порядок сохраняется, `Other` оставляйте последним: в него попадает всё, что LLM отнесла к неизвестному типу; если `Other` нет, неизвестный тип становится последним в списке):

```yaml
extract:
  entity_types:
    Person: A real or fictional individual, named or clearly identified.
    Gene: A named gene or protein; not the disease it causes (Condition).
    Condition: A disease, disorder, symptom or other medical or psychological condition.
    Other: Anything meaningful that fits none of the types above.
```

Можно указать и просто список имён без описаний: `entity_types: [Person, Gene, Other]`, или список вида `- Person: описание` / `- Gene`.

Правила проверки: список не пустой; имя не пустое и не содержит `:` или перевода строки; имена не повторяются без учёта регистра (`Person` и `person` — дубль).

Главное правило: **типы не должны пересекаться**. Тип входит в идентификатор сущности (`entity_id`), поэтому если одну и ту же вещь можно отнести к двум типам, она может расколоться на две разные сущности (например, `PyTorch` как `Software` и как `Technology`). В описании полезно прямо писать, чем тип отличается от соседних.

Что происходит после изменения типов:

- изменением считается любая правка списка: новое или удалённое имя, другое описание и даже другой порядок типов (меняется промпт);
- новые и изменённые документы сразу извлекаются с новыми типами (ключ кэша извлечения включает подпись набора типов);
- уже загруженные документы сохраняют старые типы. `status`, `doctor` и `ingest` предупреждают об этом, пока остаётся хотя бы один документ, извлечённый со старыми типами;
- чтобы переизвлечь всё с новыми типами: `uv run mnogobase reset`, затем `uv run mnogobase ingest documents/` (это заново вызывает LLM для всех чанков).

Для раскраски новых типов в Neo4j добавьте строку вида `node.Gene { color: #...; border-color: #...; }` в [`docs/neo4j/mnogobase.grass`](docs/neo4j/mnogobase.grass) (раздел 4.1).

### 6.4 PostgreSQL

Единственный SQL backend — `database.backend: postgresql`. Адрес задаётся в `config.yaml`
(`database.host/port/name/user`), пароль — в `.env` (`POSTGRES_PASSWORD`, имя переменной —
`database.password_env`). Полный DSN в переменной `database.url_env` (по умолчанию `DATABASE_URL`,
`postgresql://` или `postgresql+psycopg://`), если она задана, переопределяет и адрес, и пароль.
Файловые базы и автоматический fallback не поддерживаются. Импорт старых SQLite-баз удалён.

```yaml
database:
  backend: postgresql
  host: localhost
  port: 5432
  name: mnogobase
  user: mnogobase
  password_env: POSTGRES_PASSWORD
  url_env: DATABASE_URL             # необязательный полный DSN
  schema_prefix: mnogobase
  project: default
  connect_timeout: 5
```

`POSTGRES_PASSWORD` задаёт пароль при первом создании базы в Compose, и с ним же
подключается Python (особые символы экранируются автоматически). Смена `POSTGRES_PASSWORD`
после инициализации данных сама не меняет пароль роли в БД. В `compose.yaml` контейнеры
`api` и `worker` получают только адрес сервиса `postgres` (`MNOGOBASE_DATABASE__HOST`).

Всё состояние проекта лежит в **одной схеме** `<schema_prefix>_project_<project>`
(по умолчанию `mnogobase_project_default`): registry, очередь заданий, загрузки, пользователи,
сессии, диалоги и учёт LLM (раздел [5.4](#54-модель-данных)). Для другого самостоятельного
проекта задайте другое `database.project`, а также отдельные Qdrant prefix, Neo4j и файловые
каталоги (раздел [7.14](#714-отдельные-проекты)). PostgreSQL namespace не зависит от cwd.
`database.schema_prefix` — `[a-z][a-z0-9_]{0,15}`, `database.project` —
`[a-z][a-z0-9_]{0,36}`; составные имена укладываются в лимит PostgreSQL. Таблицы создаются
при первом обращении (`CREATE ... IF NOT EXISTS` под advisory lock); разрушающих миграций нет.

При `ingest` создаётся локальный `.mnogobase/postgresql-project.json` с
идентификатором подключения без пароля. Он сохраняет защиту читающих команд и
`reset --yes` от запуска из чужого каталога. Старые eval run.json после смены
настроек продолжают хранить старый снимок: начинайте новый каталог опыта.

Резервная копия PostgreSQL в режиме разработки (каталог backups создайте заранее):

```bash
docker compose exec -T postgres pg_dump -U mnogobase -d mnogobase -Fc > backups/mnogobase.dump
```

На сервере холодную копию PostgreSQL вместе с Qdrant, Neo4j, wiki и документами делает
`deploy/backup.sh` (раздел [11](#11-развёртывание)): части одного проекта нужно сохранять и
восстанавливать вместе.

PostgreSQL не меняет модель обработки: один worker и один писатель корпуса.
Wiki, документы и кэши остаются на файловой системе. Для нескольких машин
потребуются согласованное файловое хранилище и отдельная доработка worker.

## 7. Как поменять типовые вещи

### 7.1 Локальная LLM

Для закрытых документов — ничего не уходит наружу. В `config.yaml`:

```yaml
llm:
  model: unsloth/Qwen3-30B-A3B-Instruct-2507-GGUF:Q4_K_M     # llama.cpp: GGUF с квантом, ~18 ГБ
  serve: llamacpp
  # base_url уберите: по умолчанию это локальный http://localhost:8000/v1
```

Строку `base_url` с адресом внешней LLM удалите или задайте `base_url: null`: значение по умолчанию — локальный сервер на порту 8000. Через `.env` эквивалент — `MNOGOBASE_LLM__BASE_URL=http://localhost:8000/v1`. Готовый сервер на другой машине подключается как `serve: api` с его `base_url` (раздел 7.2).

Затем `uv run mnogobase models up` поднимет и LLM. Ключ не нужен. Проверка: `uv run mnogobase doctor` (строка `llm`). Последствия: модель входит в ключ кэша извлечения, поэтому новые и изменённые документы извлекаются новой моделью, а уже загруженные остаются как есть; для полного переизвлечения — `reset` и `ingest`. Параллелизм ограничивают и `llm.concurrency`, и число слотов сервера (у llama.cpp — `--parallel`, задаётся в `llm.server.args`). `llm.overrides` с другими именами моделей работает только с `api`: локальный сервер держит одну модель.

### 7.2 Другой OpenAI-совместимый эндпоинт

llama.cpp server, LM Studio, OpenRouter, OpenAI или корпоративный прокси подключаются одинаково:

```yaml
llm:
  base_url: http://localhost:8000/v1    # адрес до /v1 включительно
  model: <имя модели на этом сервере>
  api_key_env: MY_PROVIDER_KEY          # и MY_PROVIDER_KEY=... в .env
```

Требование к серверу: `POST /chat/completions` с `response_format` типа `json_schema` и `strict: true` — так работают извлечение и слияние сущностей. Если сервер это не поддерживает, этап `extract` будет падать (см. раздел 8.3, «Новый провайдер LLM»). Блоки `<think>...</think>` из ответов модели вырезаются автоматически, а у JSON-ответов — и обёртка блоком кода.

### 7.3 Разные модели под задачи

```yaml
llm:
  model: gpt-6-luna
  overrides: {extract: <дешёвая модель>, resolve: null, wiki: null, answer: <сильная модель>}
```

Задачи: `extract` (сущности и связи по чанкам — больше всего вызовов), `resolve` (проверка «одна ли сущность» и сжатие описаний), `wiki` (страницы), `answer` (ответы), `query` (перевод вопроса). Override меняет только имя модели: адрес и ключ общие (`llm.base_url`). Смена модели `extract` меняет ключ кэша, как в 7.1.

### 7.4 Сменить эмбеддер или размерность

Пример: Qwen3-Embedding-0.6B (1024 измерения) на llama.cpp. В `config.yaml`:

```yaml
embedder:
  model: Qwen/Qwen3-Embedding-0.6B-GGUF:Q8_0
```

`embedder.dim` по умолчанию `auto`: размерность новой модели берётся у сервера, править её не нужно.

1. `uv run mnogobase models up` — перезапустит эмбеддер с новой моделью (остальные серверы не трогает).
2. `uv run mnogobase reindex` — удалит коллекции Qdrant, создаст их заново с новой размерностью и пересчитает все векторы. Ничего удалять вручную не нужно.

`chunking.tokenizer: auto` сам подхватит токенайзер новой модели. У всех Qwen3-Embedding он один и тот же (отличаются только служебные `<think>`/`<tool_response>`), так что границы чанков при переходе между размерами модели не меняются.

Подпись индекса — это бэкенд, веса (у llama.cpp — GGUF с квантом), размерность и шаблоны. Пока `reindex` не выполнен, `ingest`, `wiki build`, `ask` и `compare` отказываются работать: при новой размерности предварительная проверка пишет `mb_chunks has dim 2560, embedder 1024: run mnogobase reindex` (с явным числом в `embedder.dim` — `config 1024`), при других весах или бэкенде — `index was built with llamacpp:Qwen/Qwen3-Embedding-4B-GGUF:Q4_K_M:2560:tpl-..., config now uses ...; run mnogobase reindex`. Поэтому перевод эмбеддера с llama.cpp на внешний сервер (`serve: api`) или смена кванта тоже требуют `reindex`, а после правки одних `doc_template`/`query_template` в сообщении будет `embedder templates changed`. Индексы, построенные до `serve` (подписи `ollama:...` и `openai:...`), тоже требуют `reindex`.

**Matryoshka (MRL):** Qwen3-Embedding можно использовать в меньшей размерности — поставьте `embedder.dim: 1024` (или 512) без смены модели и выполните `reindex`. Переход с явной полной размерности на `auto` (и обратно) у той же модели подпись индекса не меняет и `reindex` не требует. Векторы меньше, поиск быстрее, качество немного ниже. Если размерность больше той, что выдаёт модель, `reindex` остановится до изменения индекса: `embedder check failed: model returned N dims, config expects M; nothing was changed`.

Токенайзер (`chunking.tokenizer: auto` следует за моделью эмбеддера) влияет только на чанкинг новых и изменённых файлов.

### 7.5 Размер чанка

`chunking.max_tokens` (512 по умолчанию). Меньше — точнее поиск и больше вызовов LLM на `extract`; больше — меньше вызовов, но грубее цитаты. Применяется к новым и изменённым файлам; для всего корпуса — `reset` и `ingest`. Сервер эмбеддера не обрезает слишком длинный вход, а отклоняет его (окно — `embedder.server.ctx`, по умолчанию 8192 токена; в `compose.yaml` — `--ctx-size 4096` в команде сервиса `embed`), поэтому не ставьте предел выше окна эмбеддера.

### 7.6 OCR

`parsing.ocr: false` заметно ускоряет разбор «цифровых» PDF (с текстовым слоем), но сканы и скриншоты тогда дадут пустой текст. OCR работает только там, где у PDF нет текстового слоя (сканы, растровые области), и на файлах-картинках.

Языки — `parsing.ocr_lang` (по умолчанию `["iso:ru", "iso:en"]`). Docling сам выбирает движок (на Mac обычно RapidOCR), а RapidOCR работает с одним языком — первым из списка; его кириллическая модель читает и латиницу. Без `ocr_lang` RapidOCR берёт китайскую модель, и русский текст не распознаётся совсем. Модели OCR качаются при первом разборе (несколько МБ). Настройки действуют на новые и изменённые файлы.

### 7.7 Новые форматы файлов

Если формат поддерживает Docling, достаточно добавить расширение в `parsing.extensions`, например `[..., odt, epub, rtf, tex, xhtml]`. Список форматов установленного Docling:

```bash
uv run python -c "from docling.datamodel.base_models import FormatToExtensions as F; [print(k.value, v) for k, v in F.items()]"
```

Картинки (`png`, `jpg`, ...) уже в списке: они идут тем же конвейером, что и PDF (разметка, OCR, описание VLM). Некоторым форматам нужны дополнительные зависимости Docling — проверьте на одном файле. Форматы, которых нет в Docling, требуют кода (раздел 8.3).

### 7.8 Типы сущностей

См. раздел [6.3](#63-типы-сущностей).

### 7.9 Wiki: язык, порог, число доказательств

```yaml
wiki:
  language: ru        # en и ru превращаются в English / Russian, другое значение передаётся как есть
  min_mentions: 3
  evidence_k: 16
```

Затем `uv run mnogobase wiki build --all`. Имена сущностей, заголовки страниц и служебные разделы `Related`/`Sources` остаются английскими (имена извлекаются как канонические английские). Если `min_mentions` повысить, страницы сущностей ниже нового порога удаляются, только когда сущность снова попадёт в очередь (новое упоминание или удаление документа).

### 7.10 Поиск и ответы

`retrieval.k` (или `--k` в команде), `retrieval.context_tokens` (сколько контекста получает LLM — влияет на стоимость и качество), `retrieval.budget` (доли режимов в `all`, сумма не обязана быть 1). Действует сразу; `config_hash` в `compare.jsonl` меняется, так что прогоны с разными настройками легко различить.

### 7.11 Режим graph

`graph.hops` (1–3: больше — шире контекст и шум), `graph.seeds` (сколько стартовых сущностей брать из векторного и полнотекстового поиска), `graph.seed_threshold` (понизьте, если `graph` часто отвечает «нет источников»), `graph.max_relations`. Действует сразу. Страницы wiki всегда берут до 30 связей сущности независимо от `graph.max_relations`.

### 7.12 Слияние сущностей

`resolve.auto_merge` ниже 1.0 — часть слияний без LLM (дешевле) и риск склеить разные вещи; `resolve.llm_check` ниже — больше вопросов к LLM и меньше пропущенных дублей. Значения по умолчанию выбраны замером на 361 размеченной вручную паре сущностей из статьи по астрономии и брошюры о Солнечной системе (вердикты — LLM `resolve` из `config.yaml`):

| Политика | Слито | Ошибочно | Пропущено |
|---|---|---|---|
| `auto_merge 0.92`, `llm_check 0.80`, без ключа имени (было) | 32 | 7 | 31 из 56 |
| `auto_merge 0.97`, `llm_check 0.80` | 27 | 2 | 31 из 56 |
| `auto_merge 1.0`, `llm_check 0.80`, с ключом имени | 42 | 1 | 15 из 56 |
| `auto_merge 1.0`, `llm_check 0.75`, с ключом имени (сейчас) | 58 | 2 | 0 из 56 |

Вектор ошибается и при очень высоком косинусе: `Gap depth method` → `Gap width method` (0.988), `WMT 2014 English-to-French` → `English-to-German` (0.968), `X. Zhang` → `H. Zhang` (0.962), а верные пары начинаются с 0.5. В журнале 111 прошлых слияний (статьи о Transformer и BERT) по одному вектору верны 16 из 47, после проверки LLM — 52 из 54 однозначных. Пары ниже 0.75 размечены только среди найденных по ключу имени, поэтому «0 пропущенных» — оценка сверху. Действует на новые слияния; уже слитые сущности не разделяются (для пересборки графа — `reset` и `ingest`). Результаты видны в логе (`entity_merged`, раздел 4.5).

### 7.13 Промпты

Промпты лежат в `src/mnogobase/llm/prompts/` и подставляются через `string.Template` (`$name`; буквальный `$` пишется как `$$`). Пакет установлен в режиме редактирования, поэтому правки действуют без переустановки.

| Файл | Задача | Плейсхолдеры | Когда действует |
|---|---|---|---|
| `extract.md` | сущности и связи из чанка | `$entity_types`, `$title`, `$headings`, `$text` | см. ниже |
| `resolve_same.md` | одна ли это сущность | `$a_name`, `$a_type`, `$a_description`, `$b_name`, `$b_type`, `$b_description` | новые слияния |
| `resolve_summarize.md` | сжать описания сущности | `$name`, `$type`, `$descriptions` | новые слияния |
| `wiki_page.md` | тело wiki-страницы | `$language`, `$name`, `$type`, `$description`, `$aliases`, `$relations`, `$evidence`, `$example_id`, `$existing` | `wiki build --all` |
| `answer.md` | ответ с цитатами `[n]` | `$question`, `$context`, `$language` | сразу |
| `translate_query.md` | перевод вопроса на английский для поиска | `$question` | сразу |
| `chat_query.md` | переформулировка уточнения в чате API по истории диалога (задача `query`) | `$question`, `$history` | сразу |

- **Кэш извлечения.** Ключ кэша — `(chunk_id, prompt_version, model)`, где `prompt_version` = `PROMPT_VERSION` из `src/mnogobase/extraction/extractor.py` (сейчас `extract-v4`) плюс подпись набора типов. **Меняете смысл `extract.md` — увеличьте `PROMPT_VERSION`**, иначе чанки с кэшем получат старые результаты. Уже загруженные документы сами не переизвлекаются; для всех — `reset` и `ingest`.
- Новый плейсхолдер нужно передать из кода (`render(...)` в месте вызова) и добавить в `tests/unit/test_templates.py`: тест проверяет, что в промпте не осталось `$`.
- Поля JSON-ответов задаются схемами в коде (`ExtractionResult` в `models.py`, `SameEntity` и `MergedDescription` в `extraction/resolver.py`), промптом их не поменять.

qdrant: {prefix: pb_}

database: {project: project_b}   # отдельная схема PostgreSQL: registry, очередь, пользователи
```

```bash
uv run mnogobase -c project-b.yaml ingest documents-b/
```

Qdrant можно делить между проектами через `qdrant.prefix`. **Neo4j делить нельзя:** код пишет в базу по умолчанию, а `reset` удаляет в ней все узлы. Поднимите второй экземпляр, например `docker run -d --name neo4j-b -p 7475:7474 -p 7688:7687 -e NEO4J_AUTH=neo4j/mnogobase-dev neo4j:5.26-community`.

### 7.15 Где работают модели (serve)

У каждой роли — эмбеддера, реранкера, VLM (`vision`) и LLM — своё поле `serve`:

| `serve` | Что это | Кто запускает |
|---|---|---|
| `llamacpp` | llama.cpp server с квантизованным GGUF из `model` (`repo:квант`); мало памяти, работает на Mac (Metal) и на CPU | при разработке — `mnogobase models up` (нативный `llama-server`); в полном стеке — сервисы `embed`, `rerank`, `vision` из `compose.yaml` |
| `api` | уже работающий OpenAI-совместимый сервер или облачный API по `base_url` (llama.cpp на другой машине, LM Studio, OpenAI-совместимый провайдер) | вы |

Роли независимы, их можно смешивать. Например, эмбеддер и реранкер на llama.cpp, LLM — llama.cpp на отдельной машине:

```yaml
embedder: {model: Qwen/Qwen3-Embedding-4B-GGUF:Q4_K_M, serve: llamacpp}
rerank:   {enabled: true, model: gorse-io/Qwen3-Reranker-4B-GGUF:Q4_K_M, serve: llamacpp}
llm:      {model: Qwen/Qwen3-8B, serve: api, base_url: http://llm-host:8000/v1}
```

**Что писать в `model`** зависит от `serve`. Под этим же именем модель видна на сервере (llama.cpp получает его как `--alias`), по нему `doctor` проверяет `/v1/models`.

- `llamacpp` — GGUF-репозиторий с квантом, `repo:квант`. Варианты — на странице GGUF-репозитория на Hugging Face (`*-GGUF`, файлы `*-Q4_K_M.gguf`, `*-Q8_0.gguf` и т. д.). Токенайзер зашит в GGUF, исходный HF-репозиторий модели не нужен.
- `api` — имя модели на сервере, как его отдаёт `/v1/models`. `base_url` обязателен (`base_url is required for serve: api`).

`gguf` — необязательное поле для `llamacpp`: если модель на сервере нужно назвать иначе, чем веса, `model` остаётся именем, а запускается `gguf` (`repo:квант`). Подпись индекса зависит только от бэкенда и весов, поэтому перенос того же GGUF из `gguf` в `model` не требует `reindex`.

**Команды** (по `config.yaml`, только для `serve: llamacpp`):

```bash
uv run mnogobase models up               # поднять все роли с serve: llamacpp и дождаться /health
uv run mnogobase models up embedder      # только одну роль
uv run mnogobase models status           # роль, serve, веса, адрес, готовность
uv run mnogobase models logs rerank -f   # лог сервера роли
uv run mnogobase models down             # остановить (скачанные модели остаются в кэше)
```

`models up` сначала печатает команду каждого сервера (`llama-server ...`), затем, пока серверы поднимаются, раз в 15 с — состояние каждого не готового по его `/health`:

```
embedder → http://localhost:8001/v1: llama-server -hf Qwen/Qwen3-Embedding-4B-GGUF:Q4_K_M --alias ...
[0:00] embedder: starting or downloading the model (server log: `mnogobase models logs embedder -f`)
[0:45] embedder: loading the model (server log: ...)
[0:52] embedder: ready
[0:52] All model servers are ready.
```

«starting or downloading» — сервер ещё не отвечает (запускается или качает веса; размер загрузки сервер не сообщает), «loading the model» — `/health` отвечает 503, веса грузятся в память. Предел ожидания — `--timeout` (1800 с).

Серверы — фоновые процессы `llama-server` из `PATH` (на Mac `brew install llama.cpp`; без него — `llama-server not found`). Состояние (pid и аргументы) хранится в `.mnogobase/models/<роль>.json`, вывод — в `logs/models-<роль>.log`. Роли запускаются по очереди. `models up` не перезапускает работающий сервер с теми же аргументами; после правки `config.yaml` перезапускается только изменившаяся роль, а сервер роли, ставшей `api` или отключённой, останавливается. `device: cpu` запускает серверы с `--n-gpu-layers 0`, иначе слои уходят на GPU (Metal на Mac). Эмбеддер получает `--embedding`, реранкер — `--rerank`.

В полном стеке (`compose.yaml`, раздел [11](#11-развёртывание)) `models up` не нужен: серверы `embed`, `rerank` и `vision` — CPU-контейнеры llama.cpp с явными командами, приложение обращается к ним по адресам внутри сети Compose. Модели в `compose.yaml` должны совпадать с `config.yaml`; при смене модели правятся оба места, а эмбеддер ещё требует `reindex`.

Особенности:

- **llama.cpp, реранкер.** Нужен GGUF с классификатором Qwen3-Reranker (`gorse-io/Qwen3-Reranker-4B-GGUF` по умолчанию, есть и 0.6B); старые конвертации (`dengcao`, `mradermacher`, `QuantFactory`) загружаются, но дают бессмысленные оценки.
- **Окно контекста** — `<роль>.server.ctx`. Длинный вход сервер не обрезает, а отклоняет: окно эмбеддера должно вмещать `chunking.max_tokens` плюс шаблон.
- **Дополнительные флаги** сервера — `<роль>.server.args`, например `["--parallel", "8"]` для llama.cpp.
- **Ключ API.** Если сервер требует ключ, задайте `<роль>.api_key_env` — имя переменной из `.env`.
- **Таймаут** одного запроса к серверу роли — `<роль>.timeout_s` (120 с).
- **VLM на llama.cpp.** Нужен GGUF-репозиторий с проектором картинок (`mmproj-*.gguf`): `-hf` скачивает и подключает его сам, в логе сервера — `loaded multimodal model`.

### 7.16 Картинки и графики (vision)

OCR только извлекает текст, и подписи внутри графика или схемы обычно не попадают в чанк: Docling считает такую область картинкой. При `vision.enabled` каждую картинку описывает VLM (по умолчанию Xiaomi-OCR-0 Q6_K на llama.cpp, порт 8003): что изображено, оси и ключевые значения графика, дословный текст. Описание встаёт в документ рядом с картинкой (после подписи `Figure ...`) и дальше работает как обычный текст: эмбеддинг и поиск, извлечение сущностей в граф, цитаты в ответах и wiki со ссылкой на документ и страницу. Модель выбирается через `vision.model`; OCR Docling настраивается отдельно через `parsing.ocr` и `parsing.ocr_lang`.

Для Xiaomi-OCR-0 в `config.yaml` задано `vision.server.args: ["--image-min-tokens", "1024"]`. Это минимум визуальных токенов llama.cpp: в локальной проверке без него маленькая схема, выделенная из PDF, получила выдуманное описание постороннего графика. С этим параметром та же схема описана правильно, в том числе при повторном разборе PDF.

Как Docling отбирает картинки:

1. Модель разметки находит на странице области «картинка» (в PDF, DOCX, PPTX и файлах-картинках).
2. Картинки меньше `vision.min_area` площади страницы пропускаются.
3. Классификатор Docling определяет тип (графики, схемы, фото, логотипы, ...); классы из `vision.skip` с вероятностью ≥ 0.5 пропускаются.
4. Остальные уходят на `POST <vision.url>/chat/completions` (`vision.concurrency` параллельно).

Файл-картинка (скриншот) описывается ещё и **целиком**: разметка находит в скриншоте текст и таблицы, а не картинку. Описание VLM идёт первым, за ним текст OCR. В локальной проверке Xiaomi-OCR-0 сохранила русские названия товаров и все числа контрольной таблицы, но добавила неверный английский перевод слова «Ручка» — «Booklet».

Включение:

```bash
# config.yaml: vision.enabled: true (модель и сервер — ключи vision.*, раздел 6.1)
uv run mnogobase models up vision    # ~0.84 ГБ: Xiaomi-OCR-0 Q6_K и проектор картинок
uv run mnogobase doctor              # строка models: vision ... available
```

Особенности:

- **Применяется к новым и изменённым файлам.** Уже загруженные документы разобраны без описаний; чтобы описать их картинки — `reset` и `ingest` (кэш извлечения привязан к `chunk_id`, поэтому частичный повторный разбор не годится).
- **Скорость.** Три прямых запроса к Xiaomi-OCR-0 Q6_K на Mac с `--image-min-tokens 1024` заняли 0.89–1.22 с на картинку. Это контрольные таблица, график и схема; время загрузки модели и разбора Docling сюда не входит.
- **Ошибки VLM не проходят молча.** Docling при ошибке API оставляет описание пустым; `mnogobase` в этом случае завершает этап `parse` ошибкой (`VisionError`), и файл повторяется через `ingest --retry-failed`.
- **Качество.** Локально проверены реальные ответы Xiaomi-OCR-0 и разбор PNG, DOCX и PDF: описания сохраняются в кэше и попадают в чанки, у PDF сохраняются номера страниц. Все контрольные числа и подписи присутствовали. При этом в описании выделенного графика модель ошибочно назвала разные столбцы одинаковыми по высоте; совпадение чисел не гарантирует верность выводов. Другие варианты — `vision.model: unsloth/Qwen3-VL-8B-Instruct-GGUF:Q4_K_M` (~6 ГБ) или мультимодальный OpenAI-совместимый API: `vision: {serve: api, base_url: ..., model: ..., api_key_env: ...}`.
- **Язык описания** — английский (промпт на английском), как и канонические имена сущностей; текст с картинки переписывается на его языке.

### 8.2 Узкие интерфейсы

Сменные части спрятаны за протоколами (`typing.Protocol`, реализация не наследуется — достаточно тех же атрибутов и методов):

```python
# embedding/base.py
class Embedder(Protocol):
    model_id: str
    dim: int
    templates: tuple[str, str]  # (document, query) templates the embedder applies

    def embed_documents(self, items: Sequence[EmbedInput]) -> list[list[float]]: ...
    def embed_query(self, query: str) -> list[float]: ...


class SparseEncoder(Protocol):
    def encode_documents(self, texts: Sequence[str]) -> list[qm.SparseVector]: ...
    def encode_query(self, text: str) -> qm.SparseVector: ...


# llm/client.py
class LLMClient(Protocol):
    usage: Usage  # накопленные tokens_in / tokens_out

    def model_for(self, task: str) -> str: ...
    async def complete(self, messages: list[Message], *, task: str) -> str: ...
    async def structured(
        self, messages: list[Message], schema: type[T], *, task: str, max_repairs: int = 2
    ) -> T: ...


# retrieval/base.py
class Retriever(Protocol):
    def retrieve(
        self, query: str, k: int, alt_queries: Sequence[str] = ()
    ) -> list[ContextItem]: ...
```

`EmbedInput` (`models.py`) — `modality` (`text`; `image` и `audio` зарезервированы), `text`, `path`, `title`. `task` у LLM — одно из `extract`, `resolve`, `wiki`, `answer`, `query`: выбирает модель через `llm.overrides` и попадает в логи.

Хранилища (`QdrantStore`, `GraphStore`), `Registry`, `DoclingParser` и `Chunker` — конкретные классы без протоколов.

Связывание происходит в `app.py`:

```python
def build_app(settings, *, embedder=None, sparse=None, llm=None, reranker=None, vectors=None, graph=None) -> App
```

Всё, что не передано, создаётся по настройкам: `OpenAICompatEmbedder`, `ApiReranker` (при `rerank.enabled`), `BM25Encoder`, `QdrantStore.from_settings`, `GraphStore.from_settings`, `OpenAICompatLLM` (каждая попытка вызова записывается в `llm_usage`). Тесты передают сюда фейки. Тот же `build_app` использует и `KnowledgeBase` HTTP API. Режимы поиска собирает `retrieval/__init__.py: build_retrievers(...)` — словарь `{режим: Retriever}`.

### 8.3 Рецепты расширения

**Новый эмбеддер** (например, sentence-transformers или облачный API):

1. Сначала проверьте, нельзя ли обойтись без кода: любой сервер с OpenAI-совместимым `/embeddings` (LM Studio, TEI, облачный API) подключается как `embedder.serve: api` с `base_url` и `model`. Новый **локальный бэкенд запуска** (как llama.cpp) добавляется в `model_servers.py`: значение `Serve` в `config.py`, аргументы в `server_args`, раннер; для полного стека — сервис в `compose.yaml`.
2. Иначе — класс в `src/mnogobase/embedding/<name>.py` с атрибутами `model_id`, `dim`, `templates` и методами `embed_documents`, `embed_query` (образец — `OpenAICompatEmbedder`). Используйте помощники из `embedding/base.py`: `format_document(item, template)`, `format_query(query, template)` и `truncate_normalize(vec, dim)` (обрезка Matryoshka и L2-нормировка), а для HTTP — `retryable`, `post_json_with_retry` и `auth_headers` из `mnogobase/http.py`.
3. `model_id` должен быть уникальным с префиксом провайдера (как `openai:<model>`): подпись `model_id:dim:tpl-<хеш templates>` (`embedder_signature`) сохраняется в `meta` и защищает индекс от смешивания векторов. Если провайдер не использует шаблоны, задайте `templates` постоянными.
4. `config.py`: поле в `EmbedderSettings`, по которому выбирается класс; выбор — в `build_app` (`app.py`) и в проверке `index` (`doctor.py`). Проверка `models` и `chunking.tokenizer: auto` рассчитаны на OpenAI-совместимый `/v1/models`; для другого API адаптируйте `_served_models` (`doctor.py`) или задайте HF-репозиторий в `chunking.tokenizer`. Набор проверок команд задан в `cli.py` (`PREFLIGHT_CHECKS`, `INGEST_CHECKS`, `REINDEX_CHECKS`).
5. Тесты по образцу `tests/unit/test_embedding.py` (HTTP через `httpx.MockTransport`). После переключения — `reindex` (раздел 7.4).

**Новый провайдер LLM.** Почти всегда хватает `OpenAICompatLLM` (раздел 7.2). Свой клиент нужен, если API не OpenAI-совместимый или не умеет `json_schema`:

1. Класс с `usage: Usage`, `model_for(task)`, `async complete(...)`, `async structured(...)`. Переиспользуйте `strict_json_schema(schema)`, `clean_json(text)`, `strip_think(text)` из `llm/client.py`; `structured` должен вернуть провалидированную pydantic-модель и при ошибке повторить запрос с текстом ошибки (как в `OpenAICompatLLM`).
2. Ограничьте параллелизм семафором на `llm.concurrency` (извлечение и wiki вызывают LLM параллельно) и копите токены в `usage` — их читает `compare`.
3. Выбор класса — в `build_app` (новое поле в `LLMSettings`); проверку `llm` в `doctor.py` адаптируйте к API.

**Новый режим поиска:**

1. Класс с `retrieve(self, query: str, k: int, alt_queries: Sequence[str] = ()) -> list[ContextItem]` (`alt_queries` — другие формулировки вопроса, например английский перевод; ищите и по ним) в `src/mnogobase/retrieval/<name>.py`. `ContextItem.kind` — одно из `chunk`, `wiki`, `relation`, `entity` (`models.py`); для цитат с файлом и страницей отдавайте элементы `chunk` с `path` и `page`.
2. Добавьте значение в `Mode` и в словарь `build_retrievers` (`retrieval/__init__.py`). `ask --mode` и `compare` подхватят режим автоматически (`compare` проходит по всем ретриверам).
3. Чтобы режим участвовал в `all`, добавьте его в `parts` `CombinedRetriever` и долю в `retrieval.budget`.
4. Тесты — по образцу `tests/unit/test_retrieval.py` (Qdrant `:memory:`) или интеграционные для графа.

**Новая команда CLI.** Команды — функции с `@app.command()` в `cli.py` (подкоманды wiki — `@wiki_app.command(...)`). Соглашения: `_settings(project=True)` для команд, которым нужен существующий проект; `_preflight(settings, checks)` перед обращением к сервисам; `_lock(settings)` для всего, что пишет; `build_app` и `application.close()` в `finally`; известные ошибки — через `_fail_cleanly` (код 2); текст из документов печатать через `escape`. Пример команды только для чтения:

```python
from mnogobase.stores.graph_store import GraphStore  # в начало cli.py


@app.command()
def top(limit: Annotated[int, typer.Option("--limit", help="How many entities.")] = 20) -> None:
    """Show the most mentioned entities."""
    settings = _settings(project=True)
    _preflight(settings, ("neo4j",))
    graph = GraphStore.from_settings(settings.neo4j)
    try:
        entities = graph.entities(min_mentions=1)
    finally:
        graph.close()
    table = Table("name", "type", "mentions")
    for e in sorted(entities, key=lambda e: -e.mention_count)[:limit]:
        table.add_row(escape(e.name), e.type, str(e.mention_count))
    console.print(table)
```

Тесты CLI — `tests/unit/test_cli.py`: `typer.testing.CliRunner`, `run_checks` и `configure_logging` подменяются фикстурой.

**Новый формат файлов.**

- Формат есть в Docling — только `parsing.extensions` (раздел 7.7).
- Формата нет в Docling — расширьте `DoclingParser.parse` (`parsing/docling_parser.py`): по расширению превратите файл в Markdown или HTML и передайте конвертеру поток `DocumentStream(name="<имя>.md", stream=BytesIO(...))` из `docling.datamodel.base_models` (метод `convert` принимает путь или поток). Остальной конвейер работает с `DoclingDocument`, поэтому `parse` должен по-прежнему сохранять JSON в кэш и возвращать `ParsedDocument`. Не забудьте добавить расширение в `parsing.extensions` и тест в `tests/unit/test_parsing_chunking.py`.

**Изменение схемы графа.** Весь Cypher — в `stores/graph_store.py`:

1. Ограничения и индексы — в список `_SCHEMA` (только `IF NOT EXISTS`: схема применяется при каждом запуске).
2. Новое свойство — в модель (`models.py`) и в соответствующий `upsert_*`; новая связь или метка — новый метод `GraphStore` и вызов из `pipeline.py` или `wiki/builder.py`.
3. Поддержите каскадное удаление: `_delete_document_tx` и `document_deletion_plan` должны убирать новые данные документа согласованно (план вычисляется до транзакции). Если данные нужны `reindex`, проверьте `doc_chunks` и `maintenance.py`.
4. Уже загруженные данные сами не мигрируют: разовый Cypher-скрипт или `reset` и `ingest`.
5. Обновите интеграционные тесты (`tests/integration/test_graph_store.py`, `test_pipeline.py`), запросы в разделе 4.1 и стиль `docs/neo4j/mnogobase.grass` для новых меток.

### 8.4 Тесты, стиль и коммиты

- **SQL-хранилища проверяются на настоящем PostgreSQL**, без подмены SQLite. Соответствующие проверки registry, очереди, service и CLI отмечены `integration`, даже если файл исторически лежит в `tests/unit/`. Каждый тест получает отдельный namespace. `MNOGOBASE_TEST_DATABASE_URL` допускает выделенный тестовый PostgreSQL вместо временного контейнера; рабочий `DATABASE_URL` тесты не используют.
- **Маркеры** (`pyproject.toml`): без маркера — модульные тесты, `integration` — нужен Docker (testcontainers), `e2e` — Docker, модели из `config.yaml` (`mnogobase models up`) и LLM. `addopts = "-m 'not integration and not e2e'"`, поэтому `uv run pytest` запускает только модульные.
- **Фейки** (`tests/fakes.py`): `FakeLLM(handler)` — детерминированный `LLMClient`, `handler(task, prompt) -> текст ответа`, вызовы копятся в `calls`; `scripted_llm_handler` отвечает по ключевым словам (`transformer`, `attention`, `внимани`, `softmax`, `vaswani`); `FakeEmbedder` — хешированный мешок слов (тексты с общими словами близки); `FakeSparse` — такой же sparse.
- **Хранилища в тестах.** Qdrant в модульных тестах — `QdrantClient(":memory:")`. In-memory фейка Neo4j нет: всё, что касается графа, — интеграционные тесты. Фикстуры `tests/conftest.py`: `qdrant_client` и `neo4j_container` (на сессию, образы `qdrant/qdrant:v1.19.2` и `neo4j:5.26-community`), `graph` (чистый `GraphStore` со схемой на каждый тест); PostgreSQL — сессионный контейнер `postgres:18`, автоматическая фикстура `isolated_database` даёт каждому тесту свой `schema_prefix`.
- **Шаблон интеграционного теста конвейера** (`tests/integration/test_pipeline.py`): `build_app(settings, embedder=FakeEmbedder(), sparse=FakeSparse(), llm=FakeLLM(scripted_llm_handler), vectors=QdrantStore(QdrantClient(":memory:"), "t_", 64), graph=graph)` с `data_dir`, `wiki.dir` и `logs_dir` во временной папке.
- **Стиль:** `ruff` (длина строки 100, правила `E, F, I, UP, B, SIM`): `uv run ruff check . && uv run ruff format --check .`.
- **Коммиты:** префиксы `feat:`, `fix:`, `docs:`; **никогда не коммитьте `.env`**. Производные данные (`.mnogobase/`, `logs/`, `runs/`, `wiki/`, `documents/`) в `.gitignore`.

Чтобы начать с чистого листа:

```bash
uv run mnogobase reset            # покажет, что удалит, и спросит подтверждение
```

**Автотесты:**

```bash
uv run pytest                    # модульные (~10 с, без сервисов)
uv run pytest -m integration     # интеграционные: сами поднимают PostgreSQL, Neo4j и Qdrant в Docker (testcontainers)

HTTP API и клиент проверяются модульными тестами (`test_api.py`, `test_client.py`, `test_user_cli.py`) и интеграционным `tests/integration/test_knowledge_base.py`. Соглашения по тестам — раздел 8.4.

### Проверки промпт-инъекций

В задачах ответа, извлечения сущностей, entity resolution, слияния описаний, сборки wiki и перевода вопроса правила приложения передаются отдельным сообщением `system`. Текст документов, метаданные, вопрос, сведения графа и существующая wiki-страница остаются в `user` как недоверенные данные. Общая политика `llm/prompts/untrusted_data.md` запрещает выполнять вложенные команды и переносить их в знания. Разделитель `<!-- untrusted-data -->` в шаблонах отделяет правила от данных **до подстановки** значений: такой же текст внутри документа не создаёт новое сообщение или роль. Выше разделителя допустимы только настройки оператора, например язык и список типов сущностей.

Офлайн-тесты проверяют роли сообщений и то, что поддельные `SYSTEM:`, разделители и переменные шаблона внутри данных не попадают в `system`:

```bash
uv run pytest tests/unit/test_prompt_injection.py tests/unit/test_templates.py
```

В `tests/security/fixtures/` лежат четыре атакующих Markdown-документа на русском и английском: подмена ответа, отмена цитирования, выдуманная сущность, поддельная системная роль и загрязнение wiki. Они отделены от обычного корпуса `tests/fixtures/`; загружать их в рабочую базу не нужно.

Отдельный запуск проверяет поведение настроенной LLM на 24 случаях: ответ с каждым видом контекста (`chunk`, `wiki`, `entity`, `relation`), извлечение сущностей и генерация wiki с атакой также в предыдущем тексте страницы. Требуются подключение `llm` из `config.yaml`, его ключ из `.env`, если сервер требует авторизацию, и модели из `llm.overrides`, если они заданы. **Запуск делает реальные запросы к LLM**, использует изолированный PostgreSQL в Docker для кэша извлечения; эмбеддер и реранкер не нужны; использует временные файлы и не пишет в рабочие Qdrant, Neo4j и wiki:

```bash
uv run pytest tests/security/test_live_prompt_injection.py -m e2e -v
```

Проверки требуют сохранить полезный факт о порте `6333` и ссылки, исключить навязанный порт `9999`, маркер атаки и вымышленную сущность. Пустой ответ или отказ вместо выполнения задачи не считается успехом. Это ограниченный регрессионный набор: офлайн-тесты не доказывают устойчивость LLM, а разделение ролей и системные правила не гарантируют полной защиты. Проверки не покрывают весь ingest/retrieval-конвейер и атаки через изображения/OCR.

Версия извлечения повышена до `extract-v4`: старые результаты не используются при новом извлечении, однако уже завершённые документы автоматически заново не обрабатываются. Для повторной генерации существующих wiki-страниц есть `mnogobase wiki build --all`; это не очищает старые сущности графа. Полное повторное извлечение требует осознанного `reset` и последующего `ingest`. В манифест `eval run` теперь входят роли сообщений и общая политика; для новых замеров нужен новый каталог эксперимента.

## 11. Развёртывание

Есть два способа запуска. Подробная инструкция для сервера — [`deploy/README.md`](deploy/README.md); здесь краткая сводка.

Всё описано в одном `compose.yaml`; данные всех баз лежат в `./data` рядом с ним (каталоги создаёт `deploy/prepare-data.sh`). Есть два способа работы с ним:

| Режим | Что запускается в контейнерах | Чем пользоваться |
|---|---|---|
| Разработка | `docker compose up -d postgres qdrant neo4j` и, по желанию, `embed rerank vision` | `uv run mnogobase ...` на Mac (модели — контейнеры или `uv run mnogobase models up`) |
| Полный стек (локально и на сервере) | `docker compose up -d`: API, worker, базы, llama.cpp `embed` / `rerank` / `vision` на CPU | `mnogobase client` и `docker compose exec api mnogobase ...` |

В обоих режимах LLM подключается по внешнему API из `config.yaml` (или локально, раздел [7.1](#71-локальная-llm)).

**Порты.** Каждый сервис открыт только на `127.0.0.1` — для программ этого же компьютера, из сети он не виден: API 8080, PostgreSQL 5432, Qdrant 6333 (сайт `http://localhost:6333/dashboard`, вход по `QDRANT_API_KEY`), Neo4j 7474 (сайт `http://localhost:7474`, пользователь `neo4j` и `NEO4J_PASSWORD`) и 7687, модели 8001 / 8002 / 8003. Это те же адреса, что в `config.yaml`, поэтому нативный CLI работает с контейнерами без настроек. Нативные `models up` занимают те же порты 8001–8003: запускайте либо их, либо контейнеры `embed` / `rerank` / `vision`. На сервере те же порты тоже только локальные; сайты баз открываются через SSH-туннель ([deploy/README.md](deploy/README.md)).

**Один писатель на базу.** Базы общие для обоих режимов, но файлы — нет: у нативного CLI wiki, кэш и метка проекта лежат в корне репозитория (`wiki/`, `.mnogobase/`), у контейнеров — в `./data/app`. Поэтому корпус пишет кто-то один: либо `uv run mnogobase ingest` / `worker run`, либо worker в Docker. Читающие команды нативного CLI видят базу полного стека только после записи из того же каталога (иначе `No mnogobase project here`); чтобы сменить режим, выполните `mnogobase reset` и загрузите документы заново.

### 11.1 Режим разработки

```bash
deploy/prepare-data.sh                     # один раз
docker compose up -d postgres qdrant neo4j embed rerank vision
uv run mnogobase doctor
uv run mnogobase api serve                 # по желанию: API на 127.0.0.1:8080 (раздел 16)
uv run mnogobase worker run --watch documents/
```

Compose требует непустые `POSTGRES_PASSWORD`, `NEO4J_PASSWORD` и `QDRANT_API_KEY` в `.env`. Модели в контейнерах работают на CPU с контекстом 4096; нативные `uv run mnogobase models up` (без `embed rerank vision` в команде выше) используют `server.ctx` и флаги из `config.yaml`. Логи контейнеров на Mac пишет драйвер `local` (ротирует сам, до ~100 МБ на контейнер); на сервере `MB_LOG_DRIVER=journald` в `.env` отправляет их в журнал хоста с его лимитом и сроком хранения (`deploy/README.md`).

### 11.2 Полный стек в Docker

```mermaid
flowchart LR
    CLIENT["mnogobase client<br/>(ноутбук)"] -- "HTTPS" --> NGINX["nginx<br/>(только сервер)"]
    NGINX --> API
    CLIENT -. "локально: 127.0.0.1:8080" .-> API
    subgraph STACK["compose.yaml · проект mnogobase-kb"]
        API["api<br/>mnogobase api serve"]
        WORKER["worker<br/>worker run --watch /data/inbox"]
        PG[("postgres")]
        QD[("qdrant<br/>API key")]
        NEO[("neo4j<br/>APOC + GDS")]

    end
    API --> PG & QD & NEO & MODELS
    WORKER --> PG & QD & NEO & MODELS
    API & WORKER -. "LLM API" .-> LLM["внешний LLM"]
```

Запуск на своей машине (нужен Docker):

```bash
cp .env.example .env                          # только секреты: LLM_API_KEY, пароли, QDRANT_API_KEY
deploy/prepare-data.sh                        # каталоги ./data/* и закреплённый jar GDS
docker compose up -d --build --wait
docker compose exec api mnogobase user create owner   # пароль от 12 символов
uv run mnogobase client login owner           # http://127.0.0.1:8080 по умолчанию
uv run mnogobase client documents upload paper.pdf
uv run mnogobase client ask "О чём статья?"
```

Первый старт скачивает GGUF-модели (несколько ГБ) в `data/models`, поэтому `--wait` может занять до получаса (у серверов моделей `start_period` 30 минут). Документы можно также класть в `data/app/inbox`: worker подхватит их сам.

Как устроен стек:

- **Образ приложения** (`Dockerfile`): Python 3.12 slim, все зависимости из `uv.lock` (один список с точными версиями, включая Ragas и pytest), пользователь с uid 10001, `MNOGOBASE_LOG_FORMAT=json` (логи в stdout). Рабочий каталог `/data` = `data/app`: там относительные пути конфига — `.mnogobase/`, `wiki/`, `documents/uploads/`, `runs/`, `inbox/`. `config.yaml` из репозитория монтируется только для чтения; кэш моделей Docling и Hugging Face — в `data/cache`.
- **Настройки**: в `.env` только секреты, всё остальное — общий `config.yaml`. `compose.yaml` переопределяет лишь адреса сервисов внутри сети Compose (`postgres`, `qdrant`, `neo4j`, `embed`, `rerank`, `vision`).
- **Модели** — образ `ghcr.io/ggml-org/llama.cpp` с явными командами, `--n-gpu-layers 0`, окно 4096. Имена моделей должны совпадать с `config.yaml` (раздел [7.15](#715-где-работают-модели-serve)).
- **Данные** — bind-каталоги `data/{app,cache,models,postgres,qdrant,neo4j,neo4j-plugins}` рядом с `compose.yaml` с `create_host_path: false`: если каталога нет (том не смонтирован), контейнер не стартует и не пишет на корневую ФС. Каталоги создаёт `deploy/prepare-data.sh`; переменная `MB_DATA` переопределяет корень (учебное восстановление).
- **Сеть и защита.** Наружу публикуется только API на `127.0.0.1:${MB_API_PORT:-8080}`; порты баз и моделей не публикуются, поэтому Neo4j Browser и панель Qdrant в этом режиме недоступны. Qdrant закрыт API-ключом, Neo4j и PostgreSQL — паролями из `.env`.
- **Ресурсы.** У каждого контейнера `mem_limit` (swap запрещён через `memswap_limit`) и `cpus`: api 1.5 ГБ / 1 CPU, worker 3 ГБ / 2, postgres 768 МБ / 0.75, qdrant 1 ГБ / 1, neo4j 2 ГБ / 2 (heap 768 МБ, page cache 256 МБ), embed и rerank по 2 ГБ / 2, vision 3 ГБ / 2 — профиль сервера на 8 vCPU / 16 ГБ, общего с другими сервисами. Логи: `non-blocking`, драйвер `local` на Mac и journald на сервере (`MB_LOG_DRIVER`). Политика перезапуска — `on-failure:5`.
- **Worker** останавливается по `SIGINT` с `stop_grace_period: 15m`: текущее задание дорабатывает шаг и остаётся в очереди до перезапуска.

Операторские команды выполняются внутри контейнера: `docker compose exec api mnogobase status | doctor | graph analyze | reindex | jobs list | user ...`.

### 11.3 Сервер

Целевая платформа — Ubuntu с Docker и отдельным смонтированным томом `/srv/mnogobase`. Шаги из [`deploy/README.md`](deploy/README.md) кратко:

1. Пакеты `docker.io docker-compose-v2 nginx certbot restic`, firewall на 22/80/443.
2. Код в `/srv/mnogobase/app` (на смонтированном томе, поэтому `data/` тоже на нём), `.env` только с секретами (`openssl rand -hex 24`), `sudo deploy/prepare-data.sh`.
3. `docker compose build`, юнит `deploy/mnogobase.service` (systemd запускает и останавливает весь стек `docker compose up -d --wait` / `stop`), затем `docker compose exec api mnogobase user create owner`.
4. HTTPS: сертификат certbot и `deploy/nginx.conf` (TLS 1.2/1.3, 444 на чужой Host, лимит тела 64 KiB и 50 МБ для загрузки документа, предел частоты на `/api/auth/login`, журнал без строки запроса).
5. Бэкапы: restic-репозиторий вне сервера, `deploy/mnogobase-backup.service` и `.timer` (ежедневно в 04:30) запускают `deploy/backup.sh`.

С ноутбука: `uv run mnogobase client --url https://kb.example.org login owner`; адрес можно сохранить в `service.api_url` или `MNOGOBASE_API_URL`.

### 11.4 Обслуживание

| Задача | Команда (на сервере — из `/srv/mnogobase/app` через `sudo`) |
|---|---|
| обновить | `deploy/backup.sh && git pull --ff-only && MB_TAG=$(git rev-parse --short HEAD) docker compose up -d --build --wait` |
| откатить | `git checkout <commit> && MB_TAG=<commit> docker compose up -d --wait` (старый образ уже есть локально) |
| состояние | `docker compose ps`, `mnogobase client status` (раздел 16) |
| логи | `docker compose logs -f api worker`, `journalctl -u mnogobase` |
| пользователь | `docker compose exec api mnogobase user passwd owner` / `user disable NAME` |
| бэкап вручную | `deploy/backup.sh`: останавливает api, worker и базы на 1–2 минуты, `restic backup` каталогов `data/{app,postgres,qdrant,neo4j}`, `.env` и `config.yaml` (модели и кэши не копируются), хранит 7 ежедневных, 4 еженедельных и 6 ежемесячных снимков |
| проверить бэкап | `restic check` и учебное восстановление в отдельный Compose-проект — команды в `deploy/README.md` |

Схема базы создаётся при старте (`CREATE ... IF NOT EXISTS`), разрушающих миграций нет. **Никогда не используйте `docker compose down -v` и `docker volume prune`**: данные лежат в `./data`, но это опасная привычка, а прежние тома разработки так удаляются без возврата.

Лимиты памяти не ограничивают рост данных на диске. Для контроля: `docker system df -v`, размер PostgreSQL — `SELECT pg_size_pretty(pg_database_size(current_database()));`. На сервере жёсткий предел даёт отдельная файловая система для `/srv/mnogobase`.

## 13. Что дальше

Текущие ограничения, которые стоит учитывать при использовании:

- Исчезнувшие файлы убираются из базы командой `remove --missing`; watcher не запускает удаление автоматически. Изменение существующего файла и переименование без правки обрабатываются инкрементально.
- Изображения ищутся через текстовые описания VLM; поиск по собственным визуальным эмбеддингам не реализован.
- Извлечение сущностей, wiki и ответы зависят от качества LLM. Номера цитат и наличие evidence помогают проверке, но не гарантируют достоверность каждой фразы.
- Wiki может содержать мало страниц на маленьком корпусе из-за `wiki.min_mentions`; graph может вернуть пустой контекст, если стартовые сущности не найдены.
- Оценка сравнивает режимы одного приложения с общей подготовкой знаний. Эти измерения не являются независимыми затратами трёх отдельно построенных систем.
- HTTP API рассчитан на одного владельца: одна база знаний на процесс, без ролей; все учётные записи видят все документы, личные у каждой только диалоги.

Вне текущего этапа:

- Веб-интерфейс поверх HTTP API, MCP-сервер, агент Deep Research.
- Поиск пробелов и противоречий в знаниях, community summaries (GDS), нормализация предикатов.
- Мультимодальные эмбеддинги картинок и аудио — поиск картинки по вопросу без текстового описания (задел: `EmbedInput.modality`, поле `modality` в payload; Docling уже сохраняет картинки в `.mnogobase/cache/<doc_id>/images/`). Сейчас картинки попадают в поиск через описания VLM (раздел 7.16).
- Langfuse-трейсинг, учёт токенов на этапах `ingest`, импорт старых `runs/compare.jsonl` в оценку.
- Веб-страницы как источник (URL → HTML → Docling).

## 14. Оценка Hybrid RAG, WikiLLM и GraphRAG

Оценка работает через пакет и CLI. По умолчанию сравниваются **существующие реализации проекта**: `rag` (Hybrid RAG), `wiki` (WikiLLM), `graph` (GraphRAG). Режим `graph` использует текущий поиск по графу проекта; эта оценка не добавляет алгоритмы Microsoft GraphRAG. Объединённый `all` можно включить явно.

```mermaid
flowchart TD
    CORPUS["Документы"] --> INGEST["eval ingest<br/>общая подготовка и измерения"]
    INGEST --> SNAPSHOT["Зафиксированный корпус<br/>индексы · граф · wiki"]
    DATASET["questions.jsonl<br/>вопросы + эталоны"] --> RUN["eval run<br/>ответы в выбранных режимах"]
    SNAPSHOT --> RUN
    RUN --> ANSWERS["answers.jsonl<br/>ответы + точные контексты"]
    ANSWERS --> SCORE["eval score<br/>LLM-судья + Ragas"]
    SCORE --> SCORES["scores.jsonl<br/>значения и статусы"]
    SCORES --> REPORT["eval report<br/>Markdown + CSV"]
    ANSWERS --> REPORT
    INGEST -. "processing.jsonl" .-> REPORT

    classDef data fill:#eff6ff,stroke:#2563eb,color:#172554
    classDef step fill:#ecfdf5,stroke:#059669,color:#064e3b
    classDef judge fill:#f5f3ff,stroke:#7c3aed,color:#3b0764
    classDef output fill:#fff7ed,stroke:#ea580c,color:#7c2d12

    class INGEST,RUN step

`eval benchmark` объединяет `run → score → report`. Судья вызывается на этапе `score`; `report` строится по файлам без моделей и сети. Схема показывает состав эксперимента, без результатов измерений: сравнение качества появляется после запуска на вашем корпусе.

### Подготовка и запуск

Из корня репозитория установите зависимости (`uv sync`). Ragas и `langchain-community` входят в общий список зависимостей и есть и в локальной установке, и в образе. Все прямые зависимости закреплены точными версиями в `pyproject.toml`: OpenAI SDK 3.3.0 совместим с Instructor из Ragas (ему нужен `jiter<0.15`), а `langchain-community` держится на 0.3.x, потому что Ragas 0.4.3 с 0.4 не импортируется.

В `eval/questions.jsonl` находится отдельная копия 40 вопросов с эталонами по статье *Attention Is All You Need*. Файл статьи пользователь помещает в `documents/`; короткие Markdown-примеры из `tests/fixtures/` не заменяют полную статью.

```bash
docker compose up -d postgres qdrant neo4j embed rerank vision
uv run mnogobase ingest "documents/Attention is all you need.pdf"
uv run mnogobase doctor

# Пробный запуск: 2 вопроса × 3 подхода. Оценка вызывает модель-судью.
uv run mnogobase eval run eval/questions.jsonl --limit 2 --output runs/eval/attention-smoke
uv run mnogobase eval score runs/eval/attention-smoke
uv run mnogobase eval report runs/eval/attention-smoke

# Полный запуск: 40 вопросов × 3 подхода × 5 метрик = 600 оценок.
# Одна оценка может потребовать несколько API-вызовов.
uv run mnogobase eval run eval/questions.jsonl --output runs/eval/attention
uv run mnogobase eval score runs/eval/attention
uv run mnogobase eval report runs/eval/attention
```

Используйте одинаковый корпус и неизменные индексы, граф и wiki для всех подходов и при возобновлении. Если в базе есть другие документы, это оценка по всей текущей базе. Для опыта только по статье подготовьте отдельный проект с отдельными `data_dir`, `wiki.dir`, префиксом коллекций Qdrant и отдельным экземпляром Neo4j. Не удаляйте рабочую базу ради примера.

`run.json` фиксирует снимок реестра выбранного проекта и wiki; изменение снимка запрещает продолжать этот запуск в том же каталоге. Во время генерации удерживается блокировка корпуса (PostgreSQL advisory lock). Прямые изменения в Qdrant/Neo4j внешними инструментами снимок может не обнаружить, поэтому на время опыта их тоже исключите. Порядок измерений build/update — в [разделе 15.2](#152-измерение-build-и-update).

`--mode` можно повторять: `--mode rag --mode graph --mode all`. `--k 8` задаёт число результатов retrieval. Для выбора метрик используйте повторяемый `eval score ... --metric faithfulness --metric factual_correctness`; последующий запуск без `--metric` досчитает остальные. Глобальный `--config` передаётся **до** `eval`.

### Судья и метрики

`evaluation` в `config.yaml` задаёт независимое подключение судьи. Незаданные (`null`) адрес, модель и имя переменной ключа наследуются из `llm` и `embedder`. Для независимой оценки лучше выбрать отдельную модель-судью; использование генератора как судьи может влиять на результаты.

```yaml
evaluation:
  base_url: https://judge.example/v1
  model: judge-model
  api_key_env: JUDGE_API_KEY
  embedding_url: http://localhost:8001/v1
  embedding_model: embedding-model
  embedding_api_key_env: ""  # локальный сервер без ключа
  timeout_s: 360
  temperature: 0
  strictness: 3
```

В `.env` запишите `JUDGE_API_KEY=...`. Если имя переменной ключа задано, но значение отсутствует, команда сообщает ошибку; чужой ключ не подставляется. Пустое имя (`""`) означает локальный сервер без авторизации. Все настройки доступны через `MNOGOBASE_EVALUATION__...` (примеры в `.env.example`). В манифестах сохраняются имена переменных, без значений ключей.

| Метрика | Что проверяет | Помимо LLM-судьи |
|---|---|---|
| `faithfulness` | Подтверждаются ли утверждения ответа переданным контекстом | Контекст |
| `answer_relevancy` | Насколько ответ соответствует вопросу | Embeddings судьи |
| `context_precision_with_reference` | Полезность и порядок контекстов относительно эталона | Контекст и эталон |
| `context_recall` | Покрывает ли контекст факты эталона | Контекст и эталон |
| `factual_correctness` | Совпадение фактов ответа с эталоном, F1 | Эталон |

### Прогресс, возобновление и отчёт

`run` показывает готовые и оставшиеся ответы; `score` — пары вопрос–режим–метрика. Каждая завершённая попытка сразу сохраняется. Повторите ту же команду для продолжения: успешные результаты не пересчитываются, ошибки повторяются. После обрыва восстанавливается только незавершённая последняя строка JSONL; повреждения в середине файла требуют проверки.

В каталоге запуска сохраняются:

- `run.json`: вопросы, режимы, настройки, отпечаток датасета и шаблон промпта. Смена датасета, лимита, режимов или настроек генерации требует нового каталога.
- `answers.jsonl`: ответы, полные контексты после ограничения бюджета, источники, время, токены и ошибки. Старый `compare.jsonl` не содержит полных контекстов, поэтому его нельзя использовать вместо этого файла.
- `judge.json`, `scores.jsonl`: настройки/версия судьи и оценки каждой пары. Для смены судьи нужен новый каталог запуска. Оценки изменившегося ответа считаются устаревшими.
- `details.csv`: оценки и статусы по каждому вопросу, режиму и метрике; `summary.csv` и `report.md`: сводное сравнение подходов, время и токены.
- `paired.csv`, `by_category.csv`: парные сравнения на общих успешно оценённых вопросах и разбивка по `category`.
- `processing.jsonl`, `processing.csv`, `processing_stages.csv`: попытки измеренной подготовки базы и затраты по этапам, если эксперимент содержит такие измерения.

`score` читает сохранённые контексты: повторного поиска и генерации нет, Qdrant и Neo4j ему не нужны. `report` полностью работает без сети и моделей, в том числе до начала расчёта метрик.

Сравнивайте средние вместе с числом успешных оценок: большее значение означает лучшее качество по соответствующей метрике, но разные пропуски меняют состав выборки. Отсутствие эталона/контекста даёт `skipped` с причиной, сбой API — `error`, нечисловая оценка — `undefined`; эти случаи не подменяются нулями. Время включает перевод, поиск и генерацию. Токены учитывают успешные ответы; вызовы судьи и неудачные попытки в эти суммы не входят.

В `paired.csv` разность B − A вычисляется на одинаковых успешно оценённых вопросах; 95% интервал строится paired bootstrap по 1000 перевыборкам с фиксированным seed. Для менее двух общих вопросов интервал не рассчитывается. Маленькая выборка или единичный прогон с автоматическим судьёй не доказывают превосходство режима. Проверьте часть ответов и цитат вручную; для более широкого эксперимента добавьте документы и вопросы на объединение источников, связи и ожидаемый отказ при отсутствии ответа.

Коды выхода: `0` — выбранная работа выполнена; `1` — остались ошибки/неполные ответы или выбранные оценки; `2` — некорректный вход, конфигурация, занятый каталог или ошибка предварительной проверки. `report` возвращает `0`, если отчёт построен, даже для неполного запуска. При 401/403 расчёт останавливается после сохранения ошибки; исправьте ключ/доступ и повторите команду.

### Свой датасет и проверка реализации

JSONL содержит один объект на строку: обязательные непустые строки `id` и `question`, необязательный `reference` (строка или `null`). Идентификаторы должны быть уникальны; дополнительные поля (`language`, `category`, `answerable`, страницы источника) сохраняются. `answerable` — метаданные, вопросы не отфильтровываются по этому признаку. Для вопросов без ответа в статье эталон должен описывать ожидаемый отказ и не добавлять сведений извне.

```json
{"id":"attention-scaling","question":"Зачем делить QKᵀ на sqrt(d_k)?","reference":"Масштабирование предотвращает слишком большие значения скалярных произведений и малые градиенты softmax."}
```

Тесты не делают реальных вызовов моделей: проверяются полный контекст, три режима, возобновление, ошибки и пропуски, корректность аргументов метрик, неполные отчёты и отсутствие подключений к хранилищам при `score`/`report`.

```bash
uv run pytest tests/unit/test_evaluation.py tests/unit/test_evaluation_cli.py
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv lock --check
git diff --check
```

## 15. Фоновая обработка и воспроизводимые эксперименты

### 15.1 Очередь и наблюдение

Worker запускается отдельным процессом и использует те же настройки и конвейер, что обычный `ingest`. Это единственный писатель корпуса: он выполняет и задания `ingest` (из watcher, `jobs enqueue` или загрузки через API), и задания `remove` (удаление документа через API). В полном стеке он работает как сервис `worker` (`worker run --watch /data/inbox`, раздел 11). Сначала выполните [подготовку сервисов](#22-первый-запуск-один-раз); затем:

```bash
mkdir -p documents
uv run mnogobase worker run --watch documents/
```

Пока worker работает, в другом терминале можно посмотреть очередь и повторить задания, исчерпавшие попытки:

```bash
uv run mnogobase jobs list
uv run mnogobase jobs retry
```

```mermaid

    FILE["Новый или изменённый файл"] --> STABLE["Watcher<br/>период стабильности"]
    STABLE --> QUEUE[("PostgreSQL jobs<br/>постоянная очередь")]
    MANUAL["jobs enqueue"] --> QUEUE
    API["HTTP API<br/>загрузка · удаление"] --> QUEUE
    QUEUE --> WORKER["Один worker<br/>блокировка корпуса"]

    RETRY -->|"нет"| FAILED["Задание failed<br/>jobs retry для повтора"]

    classDef work fill:#ecfdf5,stroke:#059669,color:#064e3b
    classDef retry fill:#fff7ed,stroke:#ea580c,color:#7c2d12
    class FILE,STABLE,QUEUE,MANUAL,API input
    class WORKER,PIPELINE,DONE work
    class RETRY,FAILED retry
```

Для разовой обработки очереди выполните `jobs enqueue documents/`, затем `worker run --once`. По умолчанию watcher опрашивает папки каждые 2 секунды и ждёт 2 секунды стабильности; worker допускает `jobs.max_attempts` (5) попыток задания, первая пауза повтора — `jobs.retry_delay_s` (30 с), одно задание ограничено `jobs.timeout_s` (3600 с, затем ошибка `JobTimeout`). Если недоступна база или сервер моделей (предварительная проверка как у `ingest`), задание откладывается без расхода попытки. При аварии незавершённые задания возвращаются в очередь, а этапы и кэш восстанавливает конвейер. Если содержимое изменилось после постановки, устаревшее задание заменяется новой ревизией.

Ctrl+C или SIGTERM останавливает worker; для продолжения повторите команду запуска. После `reset` неизменённые файлы нужно поставить явно через `jobs enqueue documents/ --force`: история очереди сама не очищается. `--force` повторяет задание, но не сбрасывает завершённые этапы ingest. Перед административным сбросом остановите worker.

| Параметр worker | По умолчанию | Назначение |
|---|---|---|
| `--watch PATH` | без наблюдения | повторяйте для нескольких существующих папок |
| `--interval` | `2` с | интервал опроса |
| `--settle` | `2` с | сколько должны оставаться стабильными размер и mtime файла |
| `--max-attempts` | `jobs.max_attempts` (5) | предел попыток задания |
| `--retry-delay` | `jobs.retry_delay_s` (30 с) | первая пауза повтора; затем удваивается, максимум час |
| `--once` | выключено | обработать готовую очередь и выйти; вместе с `--watch` не используется |

Наблюдатель продолжает обнаруживать файлы во время ingest и повторяет обход после перезапуска. Скрытые файлы, симлинки, неподдерживаемые расширения и каталоги результатов исключены. После удаления файла запустите `remove --missing`, чтобы убрать знания из индекса. Неудачная wiki-сборка считается ошибкой задания; при занятой блокировке корпуса попытка не расходуется. `worker --once` завершается с кодом 1, если остались ошибки или отложенные/незавершённые задания: повторите запуск, когда наступит время повтора. `jobs retry --id N` возвращает в очередь одно задание со статусом `failed`.

Для работы после закрытия терминала на macOS/Linux можно запустить процесс так:

```bash
mkdir -p logs
nohup .venv/bin/mnogobase worker run --watch documents/ > logs/worker.out 2>&1 &
```

Сохраните показанный shell PID; `kill -TERM <PID>` останавливает процесс. Тяжёлый разбор или хеширование может задержать остановку текущего вызова. Автозапуск после перезагрузки этой командой не устанавливается; для постоянной работы используйте полный стек `compose.yaml` (раздел 11).

### 15.2 Измерение build и update

Для измерения обработки и сравнения качества:

```bash
uv run mnogobase eval ingest documents/ --phase build --output runs/eval/experiment-v1
uv run mnogobase eval benchmark eval/questions.jsonl --output runs/eval/experiment-v1
```

`benchmark` объединяет `run → score → report`; `--skip-score` откладывает вызовы судьи.
Новые запуски привязаны к снимку корпуса; во время генерации ответов изменения конвейером блокируются.
Отчёт включает парные сравнения на одинаковых вопросах, категории и измерения общего preprocessing.
Неудачные попытки сохраняются, пропуски не подменяются нулями.
Затраты общего конвейера не выдаются за независимую стоимость каждой архитектуры.

`--phase build` и `--phase update` — метки измерений: они не очищают базу. Если данные уже загружены, пропуск файлов не измеряет холодное построение. После фиксации `run.json` обновление корпуса измеряйте в новом каталоге эксперимента.

Пример обновления после первого эксперимента:

```bash
uv run mnogobase eval ingest new-documents/ --phase update --output runs/eval/experiment-v2
uv run mnogobase eval benchmark eval/questions.jsonl --output runs/eval/experiment-v2
```

Используйте неизменные вопросы, модель ответов, язык, промпт и предел контекста, чтобы сравнение отражало изменения корпуса. Полный холодный опыт требует отдельного проекта и пустых хранилищ ([раздел 7.14](#714-отдельные-проекты)).

Обычный `ingest` и worker сохраняют измерения в `.mnogobase/processing.jsonl`; `eval ingest` — в каталоге эксперимента. Сохраняются все попытки, включая ошибки и прерывания. Время этапов уже входит в общее время; складывать их повторно нельзя. Учёт токенов охватывает успешные вызовы основной LLM; VLM, embeddings, реранкер, судья и неуспешные сетевые вызовы не включены. Денежная стоимость и энергопотребление не измеряются. Несоответствие измерений снимку корпуса отражается в отчёте; измерения другого проекта отклоняются.

## 16. HTTP API и клиент

HTTP API (FastAPI, `mnogobase api serve`) открывает ту же базу знаний по сети для одного владельца: загрузка и удаление документов, поиск, ответы с цитатами, личные диалоги, wiki, граф и состояние. Группа `mnogobase client` — CLI-клиент этого API, локальный или для сервера. Внутри API один долгоживущий `KnowledgeBase` (`src/mnogobase/kb.py`) поверх обычного `build_app`: чтение идёт без блокировок, как у `ask`, а загрузка и удаление только ставят задания в очередь. В корпус пишет один worker (раздел [15.1](#151-очередь-и-наблюдение)).

### 16.1 Запуск и учётные записи

В режиме разработки (раздел [11.1](#111-режим-разработки)):

```bash
docker compose up -d postgres qdrant neo4j embed rerank vision
uv run mnogobase user create owner        # пароль вводится скрыто, не короче 12 символов
uv run mnogobase api serve                # 127.0.0.1:8080; --host и --port меняют адрес
uv run mnogobase worker run               # в другом терминале: выполняет загрузки и удаления
```

В полном стеке API и worker — сервисы `compose.yaml`, а учётная запись создаётся в контейнере: `docker compose exec api mnogobase user create owner`.

| Команда | Что делает |
|---|---|
| `user create NAME` | создать учётную запись; печатает JSON с `id` и `username` |
| `user passwd NAME` | сменить пароль; все сессии пользователя отзываются |
| `user disable NAME` / `user enable NAME` | заблокировать (сессии отзываются) / разблокировать |
| `user list` | список учётных записей (JSON) |

Учётные записи создаются только из CLI на хосте API: регистрации по HTTP нет. Пароль — не короче 12 символов, хранится как хеш Argon2. Ролей нет: все учётные записи видят одну базу, личные у каждой только диалоги.

### 16.2 Работа через клиент

```bash
uv run mnogobase client login owner
uv run mnogobase client status
uv run mnogobase client documents upload tests/fixtures/attention_en.md
uv run mnogobase client jobs list
uv run mnogobase client documents list
uv run mnogobase client search "Как работает внимание?" --mode rag --k 8
uv run mnogobase client ask "Кто предложил Transformer?" --mode all
uv run mnogobase client chat open --mode all
```

`ask` и `chat send` печатают текст ответа и под ним нумерованные источники: `[1] attention_en.md, p.3  /api/documents/<doc_id>/content`. С `--json` выводится исходный ответ API (текст, источники с `cited`, режим, задержка, токены). Остальные команды печатают JSON. Режим по умолчанию — `rag`, как и в API.

```bash
uv run mnogobase client chat new --title "Transformer"
uv run mnogobase client chat list
uv run mnogobase client chat history CONVERSATION_ID
uv run mnogobase client chat send CONVERSATION_ID "Уточняющий вопрос"
uv run mnogobase client wiki list
uv run mnogobase client wiki show PAGE_ID
uv run mnogobase client graph search Transformer
uv run mnogobase client graph neighbors ENTITY_ID --depth 1 --limit 50
uv run mnogobase client documents source DOC_ID --output downloaded.md
uv run mnogobase client documents remove DOC_ID
uv run mnogobase client jobs retry JOB_ID
uv run mnogobase client logout
```

- **Адрес API:** `client --url URL`, переменная `MNOGOBASE_API_URL` или `service.api_url` (по умолчанию `http://127.0.0.1:8080`). Принимается только `http(s)` без логина, query и fragment.
- **Токен** хранится в `~/.config/mnogobase/credentials.json` (свой путь — `--credentials PATH` или `MNOGOBASE_CREDENTIALS`) отдельно для каждого адреса API. Файл заменяется атомарно с правами `0600`, символическая ссылка не принимается, пароль не сохраняется.
- **Ошибки** печатаются как `API <код>: <detail>`; тело ответа целиком клиент не выводит, код выхода 2.
- **Диалоги.** `chat open` создаёт диалог (или продолжает переданный `CONVERSATION_ID`), печатает историю и читает вопросы до `/exit` или `/quit`. Уточнение переформулируется по последним `service.history_messages` сообщениям диалога (промпт `chat_query.md`, задача LLM `query`), а ответ строится по текущим источникам базы. История хранит снимок цитат и помечает `available: false`, если загруженный исходник или wiki-страница больше недоступны.
- **Документы.** `documents list` показывает все документы корпуса, в том числе загруженные из CLI или папки; скачать (`documents source`) можно только загруженные через API (`uploaded: true`). Файл `--output` не должен существовать. `documents remove` ставит в очередь задание `remove`: worker забывает документ, как `mnogobase remove` (раздел 3.9), и удаляет загруженный через API файл; файлы вне `service.uploads_dir` остаются на диске.

### 16.3 Маршруты API

Все маршруты, кроме `/health` и `POST /api/auth/login`, требуют заголовок `Authorization: Bearer TOKEN`. Списки принимают `limit` (1–200) и `offset`.

| Маршрут | Что делает |
|---|---|
| `GET /health` | проверка живости без авторизации: `{"status": "ok"}` |
| `POST /api/auth/login` | JSON `{"username": ..., "password": ...}` → `{"token": ..., "token_type": "bearer"}` |
| `POST /api/auth/logout` / `GET /api/auth/me` | отозвать текущую сессию / `id`, `username`, `role` |
| `GET /api/documents` | документы корпуса: `id`, `name`, `status`, `uploaded`, `url` |
| `POST /api/documents?filename=NAME` | загрузка: файл — сырое тело запроса; ответ `202` с заданием очереди |
| `GET /api/documents/{doc_id}/content` | исходник загруженного документа как вложение |
| `DELETE /api/documents/{doc_id}` | поставить удаление документа в очередь; ответ — задание |
| `GET /api/jobs`, `POST /api/jobs/{job_id}/retry` | задания очереди / повтор задания `failed` |
| `POST /api/search` | `{"question", "mode", "k"}` → найденные фрагменты без генерации ответа |
| `POST /api/ask` | `{"question", "mode"}` → ответ с источниками |
| `POST /api/conversations`, `GET /api/conversations` | создать диалог (`{"title"}`) / список своих диалогов |
| `GET` / `POST /api/conversations/{id}/messages` | история диалога / новый вопрос `{"question", "mode"}` с ответом |
| `GET /api/wiki`, `GET /api/wiki/{page_id}` | страницы wiki / Markdown одной страницы |
| `GET /api/graph/search?q=...`, `GET /api/graph/{entity_id}/neighbors?depth=1..3` | поиск сущностей по имени и алиасам / окрестность сущности |
| `GET /api/status` | очередь, worker и расход LLM (раздел 16.4) |

`mode` — `rag`, `wiki`, `graph` или `all` (по умолчанию `rag`). Загрузка принимает только расширения из `parsing.extensions` и не больше `service.max_upload_mb`; файл сохраняется как `service.uploads_dir/<doc_id><расширение>`. Повторная загрузка того же содержимого возвращает уже поставленное задание, если оно актуально. Если в очереди уже `service.max_pending_jobs` заданий `pending` и `running`, API отвечает `429`. В источниках ответов пути сокращены до имени файла; у чанков есть `doc_id` и `url` исходника, у разделов wiki — `url` страницы. Пустая база даёт ответ `The knowledge base has no relevant sources for this question.`

Коды ответов: `401` — нет или недействительна сессия, `404` — нет документа, страницы или сущности, `409` — индекс требует `mnogobase reindex` или база занята, `413` — слишком большое тело или файл, `422` — неверный ввод, `429` — очередь заполнена или слишком много одновременных входов, `503` — недоступна база, хранилище или модель. Одновременно в процессе API выполняется не больше `service.max_concurrent_asks` запросов `search`, `ask` и сообщений чата; отмена HTTP-запроса не прерывает начатую операцию.

### 16.4 Состояние и учёт LLM

`GET /api/status` (`mnogobase client status`) возвращает JSON:

```json
{
  "queue": {"done": 12, "pending": 1},
  "running": [],
  "worker": {"last_seen": 1762790000.0, "alive": true},
  "llm_usage": {
    "today": [{"model": "gpt-6-luna", "currency": null, "external": true, "calls": 40,
               "tokens_in": 51200, "tokens_out": 6100, "errors": 0, "estimated_cost": null}],
    "month": []
  }
}
```

Числа в примере иллюстративные. `queue` — число заданий по статусам, `running` — выполняемые задания с прогрессом этапа. `worker.alive` — heartbeat worker моложе 120 секунд. `llm_usage` — расход с полуночи UTC (`today`) и с первого числа месяца (`month`), сгруппированный по модели, валюте и признаку внешнего API.

Учёт ведётся для каждой попытки вызова LLM через `build_app` — в CLI, worker и API: извлечение, слияние сущностей, wiki, ответы, перевод и переформулировка вопроса. Записи в таблице `llm_usage` не содержат текста промптов и ответов. Эмбеддер, реранкер, VLM и судья Ragas не учитываются. `estimated_cost` — строка Decimal или `null`, если тариф не задан. Тарифы указываются явно и применяются только к LLM с `serve: api`:

```yaml
service:
  llm_rates:
    gpt-6-luna: {currency: USD, input_per_million: "1.25", output_per_million: "2.50"}  # цены условные
```

Переменная окружения — `MNOGOBASE_SERVICE__LLM_RATES` (JSON). Новый тариф действует на новые вызовы. Оценка может отличаться от счёта провайдера; квот и блокировки по бюджету нет.

### 16.5 Безопасность

- **Учётные записи** создаются только из CLI; все маршруты, кроме `/health` и входа, требуют bearer-токен. Cookie и CSRF не используются.
- **Пароли:** не короче 12 символов, Argon2. Хеширование занимает около 64 МиБ памяти, поэтому одновременно идёт не больше двух; если слот не освободился за 5 секунд, вход получает `429`. Неудачный вход пишется в журнал как `login_failed` с хешем имени. IP за прокси банит fail2ban по журналу nginx (`deploy/fail2ban/`, 3 неудачи за 7 дней — вечный бан на 80/443).
- **Сессии:** случайные токены, в базе хранится только их SHA-256; срок — `service.session_hours` (168 часов); `logout`, `user passwd` и `user disable` отзывают сессии.
- **Размер запросов:** JSON-тело ограничено 64 KiB (`413` до разбора JSON и до проверки сессии); имя и тип загружаемого файла проверяются до чтения тела, а само тело пишется потоком во временный файл рядом с загрузками (с подсчётом SHA-256) до `service.max_upload_mb` и не копится в памяти. Двоичные форматы должны начинаться со своей сигнатуры (`%PDF-`, ZIP у DOCX/PPTX/XLSX, PNG, JPEG, TIFF, BMP, WebP), иначе `422`. В `deploy/nginx.conf` те же пределы и ограничение частоты запросов на вход.
- **Расход LLM:** `service.daily_token_limit` ограничивает токены за сутки; после него вопросы, поиск, чат и загрузки получают `429` (защита от случайного цикла или украденной сессии).
- **Нет `/docs`, `/redoc` и `/openapi.json`.** Ошибки валидации не повторяют присланные значения, непредвиденные ошибки возвращают `503` без подробностей, текст ошибок провайдера LLM не сохраняется и не возвращается. Ошибки стадий в registry и поле `error` в журнале проходят через `safe_error`: ключи (`Bearer ...`, `sk-...`, пароль в URL, `api_key=...`) заменяются на `***`, длина ограничена 500 символами. Вопросы владельца пишутся в журнал только на уровне DEBUG.
- **Исходники** отдаются как вложение (`application/octet-stream`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'`); внутренние пути в ответах заменяются именами файлов и URL API.
- **Сеть:** `api serve` по умолчанию слушает `127.0.0.1`. Наружу API публикуется только через HTTPS-прокси (раздел [11.3](#113-сервер)).
